06 · Research Assistant v4.6

`interrupt()` 不是在 Agent 里 `input()` 一下。
它把“等待人”变成可持久、可跨进程恢复的 Graph 状态。

真正的 HITL 不是让一个 Worker 卡着等三小时。LangGraph 遇到 `interrupt()` 时保存 thread state，把 JSON-serializable payload 暴露给调用方，然后结束当前执行。以后任意健康进程只要用相同 thread_id和 `Command(resume=...)` 就能继续。

2

最小代码：暂停和恢复其实是两次 invocation

resume value 会变成 node 内 `interrupt()` 的返回值。
from langgraph.types import interrupt, Command

def approval_node(state):
    approved = interrupt({
      "question": "Approve?",
      "action": state["action"],
    })
    return Command(
      goto="execute" if approved else "cancel"
    )

config = {"configurable": {"thread_id": "approval-42"}}

paused = graph.invoke(initial_state, config=config)
# paused["__interrupt__"] contains the payload

resumed = graph.invoke(
    Command(resume=True),
    config=config,
)
如果改用 event streaming，interrupt 会通过 stream 的 interrupt projection 暴露；但底层语义仍然是同一条 thread checkpoint + resume。

4
为什么 node 会“从开头重跑”？
LangGraph 恢复的是 checkpoint，不是 Python 栈帧。
def node(state):
    build_payload()       # resume 时会再跑
    write_database()      # ⚠ 也会再跑
    approved = interrupt(...)
    ...
恢复后 runtime 重新进入这个 node，并按 interrupt 调用顺序把 resume value 对应回正确的 `interrupt()`。因此 interrupt 前的代码必须能安全重复。
这是框架的确定性恢复模型，不是 bug。你前面 Agent 07 学的 replay safety 现在直接决定 node 怎么写。


5
Safe pattern：interrupt 前只做 pure proposal
副作用放在批准后的 downstream node。
❌ Unsafe
def approval(state):
    send_email(state)
    ok = interrupt(...)
    ...
resume 重跑 → email 可能重复。
✅ Safer
def approval(state):
    ok = interrupt(proposal(state))
    return Command(
      goto="execute" if ok else "cancel"
    )

def execute(state):
    send_email(state)
interrupt 前没有现实副作用。
“放到 interrupt 后面”也不等于 universal exactly-once。execute node 自己仍可能 crash/replay，所以外部 side effect 依然要结合 idempotency key、checkpoint、reconcile。


6
Approve / Reject 只是最简单的 HITL
resume payload 可以是任何 JSON-serializable 数据。
Approve
`Command(resume=True)`，继续执行原动作。
Edit
resume 一个修改后的参数对象，再由 node 校验后进入后续状态。
Feedback
resume 人的评语/补充信息，让 graph 重新规划或生成。
和 Agent 06 一样：如果批准的是高风险 ToolCall，仍然应该让 payload 带足够具体的 action details，而不是只问“是否允许 Agent 继续”。


7
Same thread_id 是硬条件
resume 不是“继续最近一次暂停”，而是继续指定 thread 的 pending interrupt。
thread_id = approval-42pause→approval-42resume ✅
thread_id = approval-42pause→approval-99resume ❌ 另一条 state
产品层应该把 `thread_id` / run_id / tenant 做明确映射，不能让客户端随便猜一个 thread id 就尝试 resume。


8
Interrupt 的几个规则，背后的原因都是“可重放”
这些不是风格建议。
规则为什么
不要把 `interrupt()` 吞进普通 try/exceptinterrupt 通过特殊控制流暂停 graph，错误捕获会破坏预期语义
不要在同一个 node 中随意重排多个 interruptresume 值按 interrupt 顺序匹配
payload 用简单 JSON-serializable 数据要跨进程/持久层暴露给调用方
interrupt 前 side effect 必须幂等或移走node resume 时从开头重跑


9
Interrupt 和我们 v4.0 ApprovalManager 怎么分工？
Graph runtime 替你做 durable pause，不替你决定业务政策。
LangGraph interrupt应用 Approval Policy
暂停 thread判断 READ_ONLY / SIDE_EFFECT / DESTRUCTIVE
持久 pending state决定谁有资格批准
resume value 回到 node绑定 exact action / fingerprint / tenant / actor
恢复 graph execution审计、过期、拒绝、二次确认等业务规则
最稳的做法是组合。Policy 决定“需不需要/谁能批准什么”，interrupt 负责“如何把 graph 稳定地停住并恢复”。
