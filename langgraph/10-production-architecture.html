Research Assistant v5.0 三层架构

同一个 run 同时存在 product identity 和 graph thread identity。
Product API / Control Plane`run_id`, tenant, status, revision, cancel, approval actor, owner, budget。
LangGraph Runtime`thread_id`, State, checkpoint, interrupt, Store, subgraph, stream。
Infrastructuredurable DB/checkpointer/store, queue/broker, worker lease/heartbeat, secrets, observability backend。
核心映射：`tenant + run_id → authorized thread_id`。客户端不应该因为知道一个 thread_id 就绕过产品权限直接 inspect / resume。

Graph 知道“执行暂停了”；RunStore 知道“产品层这个 run 正在等谁批准什么”。两个状态相互引用，但不是同一个表。

Resume 为什么必须先过 App Authorization？
`Command(resume=True)` 本身不是权限证明。
UI approve
→
tenant / actor / request-id check
→
enqueue RESUME
→
worker claim revision
→
Command(resume=True)
v5.0 `ProductionGraphBridge.resolve_approval()` 明确要求 `actor_authorized=True`，还会校验 paused Run 上保存的 `approval_request_id`。未授权 actor 即使知道 run/thread 也不能产生 RESUME job。
6
Queue duplicate 为什么要在进入 Graph 前挡住？
Checkpointer 不应该被拿来替 worker claim 做 CAS。
job expected_revision = 5
RunStore revision = 5
→ Worker A claim
→ revision = 6

同一个 job 再投递：
expected 5 != current 6
→ STALE JOB REJECTED
→ 根本不调用 graph.invoke()
两种“幂等”不要混：Run revision 防重复 worker 推进产品状态；Graph checkpoint/replay 管执行恢复；外部 Tool idempotency key 管现实副作用。三个层级缺一不可。
7
Cancellation 仍然不是 Graph END
产品取消和业务自然结束是两种语义。
Graph END
当前执行路径自然结束，通常可以生成 final result。
Product CANCEL
用户/系统要求停止。RUNNING 时应先 CANCELLING，在安全边界确认后才 CANCELLED。
如果 Tool 已经发出不可逆请求，Graph 停了也不能把现实世界回滚；仍回到 Agent 07 的 reconcile / compensation。
