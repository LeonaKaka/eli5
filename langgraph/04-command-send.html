04 · Research Assistant v4.4

有些 Node 不只是“改 State”。
它改完 State 的同时，就已经决定了下一跳。

普通 conditional edge 很适合“先由 Node 更新 State，再由独立 router 读 State 选路”。但有些决策天然是一个原子结果：我决定 route=research，同时下一步就去 research。这时 `Command(update=..., goto=...)` 更贴切。另一方面，`Send` 解决的是完全不同的问题：运行时才知道要并行启动多少个下游任务。

1

三种控制流原语先别混

Conditional Edge、Command、Send 各有清楚边界。

Conditional Edge：routing function 只负责返回下一节点；state update 通常由前一个 node 单独返回。
选择标准：固定/条件路由用 Edge；“一次决策同时产生 update + goto”用 Command；运行时动态 fan-out N 个不同输入任务用 Send。
2

Conditional Edge：状态更新和路由是两个阶段

这是 02 已经用过的经典结构。
def classify(state):
    return {"route": "research"}

def route_after_classify(state):
    return state["route"]

builder.add_conditional_edges(
    "classify",
    route_after_classify,
)
classify update
→
merged State
→
router reads State
→
next node
3

`Command`：update + goto 是同一个决策

特别适合 handoff、routing decision、状态转移等本来就不可分的操作。

decide→researchdirect
goto = —
return Command(
    update={
        "route": route,
        "events": [f"decide:{route}"],
    },
    goto=route,
)
Command 不是“更高级的 if”。只有当 state update 和 next hop 本来就是一个逻辑决策时，它才更清晰；否则把所有 Edge 都塞成 Command 反而会让图结构难读。


4
`Send`：下一步有多少个 Node 实例，编图时根本不知道
这就是动态 map-reduce / fan-out 的典型场景。
Reducer fan-in：evidence
def fan_out_queries(state):
    return [
        Send("retrieve_one", {"query": q})
        for q in state["queries"]
    ]
Send 的第二个参数是每个下游任务自己的输入。也就是说同一个 `retrieve_one` Node 可以同时存在多个 execution instance，各自拿不同 query。


5
Fan-out 能成立，Fan-in 还得靠 Reducer
并行 worker 同时更新同一个字段，没有 merge semantics 就会冲突或覆盖。
class RetrievalBatchState(TypedDict):
    queries: list[str]
    evidence: Annotated[list[str], operator.add]
    summary: str
Send q1
↘
retrieve_one
Send q2
→
evidence reducer
→
summarize
Send q3
↗
retrieve_one
如果 evidence 没有 append reducer，动态并行不是“自动帮你合并”。你仍然需要定义多个 worker update 怎样落回共享 State。


6
`Send` 和静态 parallel edge 的区别
Agent 05 的 ActionGraph 到这里有了框架对应物。
静态 fan-out
add_edge("a", "b")
add_edge("a", "c")
编图时已经知道 b/c 两条分支。
动态 Send
return [
  Send("worker", item)
  for item in state["items"]
]
运行时 items 有 2 个就跑 2 份，有 50 个就生成 50 份任务。
真正上线时仍要考虑 `max_concurrency`、外部 API rate limit、成本和队列压力；`Send` 表达并行，不代表应该无限并发。


7
并行结果的顺序不要当业务契约
Reducer 解决“怎么合并”，不等于承诺完成顺序。
如果三个 retrieval worker 同时跑：
q1 → 780 ms
q2 → 110 ms
q3 → 430 ms
不要写业务逻辑依赖“evidence[0] 一定是 q1”。更稳的做法是结果带 stable id / source / query key，需要稳定输出时最后显式排序。
并发系统里，把执行时序当数据含义，是非常常见的隐性 bug。


8
Graph Loop 仍然需要终止边界
Command 和 conditional edge 都可以形成循环；LangGraph 不会替业务判断“够了”。
def route(state):
    if enough_evidence(state):
        return END
    return "retrieve_more"
Graph runtime 还有 recursion limit 作为硬上限，但它和前面 Agent 02 的 `LoopGuard` 一样：硬上限是最后保险，不是任务完成判断。
