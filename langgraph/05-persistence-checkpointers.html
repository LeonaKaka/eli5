Checkpoint 不是“存一份聊天记录”。
它保存的是某个 thread 在每个 graph super-step 的可恢复状态。

前面 Agent 07 我们手写过 checkpoint / resume。LangGraph 把这类 graph-state persistence 做成了正式 runtime 能力：编译时注入 checkpointer，执行时提供 thread_id，每个 super-step 形成 StateSnapshot。于是你才能 inspect、resume、fault recover、time travel。

1

先把 Thread、Run、Checkpoint 分开

这三个词非常容易被混成“一个对话”。
Thread

checkpoint 的持久化命名空间。相同 `thread_id` 的多个 run 可以连续积累 graph state。

Run

一次 graph invocation / execution。一个 thread 可以经历多次 run。

Checkpoint

某个 super-step 边界上的 `StateSnapshot`，带 values / next / metadata / checkpoint_id。

thread_id 不是聊天标题。它是 checkpointer 找回这条执行历史的主键/持久 cursor；换 thread_id 就是另一套 checkpoint state。
2

最小配置：compile(checkpointer=...) + thread_id

少一个都没有真正的 thread persistence。
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {
  "configurable": {
    "thread_id": "research-42"
  }
}

graph.invoke(initial_state, config=config)
InMemorySaver 只是教学/实验。进程重启后内存就没了。生产要换持久 checkpointer；不要因为 API 名里有 Saver 就误以为它天然跨重启 durable。

4
`get_state()` 和 `get_state_history()` 是调试 Agent 的显微镜
别只盯最终 output。
latest = graph.get_state(config)

history = list(
    graph.get_state_history(config)
)

print(latest.values)
print(latest.next)
print(latest.metadata)
print(latest.config)
`get_state_history()` 返回这个 thread 的 checkpoint 历史，而且最新 snapshot 在前。你可以定位“哪个 step 后 route 变错”“interrupt 卡在哪个 task”“哪个 node 写坏了 state”。


5
Checkpoint 是 super-step snapshot，不是每一行 Python 都存一次
理解 super-step，才能理解 fault recovery。
Input
→
Checkpoint
→
Node A
→
Checkpoint

Node B

Checkpoint
如果同一 super-step 有并行节点，LangGraph 还会保存成功 task 的 pending writes；另一条支路失败后恢复时，不必无脑重跑已经成功的兄弟节点。
这和我们 Agent 07 手写的 durable boundary 是同一个问题，只是 LangGraph runtime 已经替你处理了更多 graph-level bookkeeping。


6
`update_state()` 不是修改旧快照，而是创建新 checkpoint
历史不会被“原地改写”。
before = graph.get_state(config)

graph.update_state(
    config,
    {
      "status": "reviewed",
      "events": ["manual-review"],
    },
)

after = graph.get_state(config)

assert before.config != after.config
Reducer 仍然生效。如果 `events` 是 append reducer，`update_state()` 传入一条新 event 会累积，而不是自动覆盖整列。


7
Replay / Time Travel：从旧 checkpoint 往后重新执行
“回到过去”不是把未来结果复制回来。
cp-1
→
cp-2
→
cp-3
→
cp-4
选择 `cp-2` replay 时，cp-2 之前的结果可复用；之后的 nodes 会重新执行。因此后面的 LLM call、API call、interrupt 都可能再次发生。
所以 time travel 不是“免费的撤销键”。凡是 replay 区间里的现实世界副作用，仍然必须 obey idempotency / reconciliation / compensation。


8
Checkpointer ≠ Store ≠ 我们 v4.0 的 RunStore
这三个持久层解决不同问题。
组件主要 scope存什么典型用途
Checkpointer单个 threadGraph StateSnapshotresume / HITL / time travel / fault recovery
LangGraph Store跨 thread应用定义的数据用户偏好 / 长期事实 / shared memory
App RunStore产品控制面tenant / run status / revision / cancel / ownerAPI、Queue、Worker concurrency、authorization
后面可以整合，但语义别抹平。`thread_id` 不能自动替你完成 tenant authorization；checkpoint 也不会自动替 Queue 做 worker lease。


9
Durability mode 也是工程选择
保存频率越强，一般一致性越高，成本/延迟也更高。
exit
graph 退出时持久化；性能高，但中途进程 crash 时不能依赖中间 checkpoint 恢复。
async
下一步执行时异步持久化，性能/耐久折中。
sync
下一步开始前同步写 checkpoint，更耐久但有写入开销。
不要机械地“生产就全 sync”。要看任务价值、side-effect 风险、checkpoint 大小、恢复成本和延迟预算。
