模型没有“聊天记忆魔法”。
每一轮都必须重新得到上下文。

你在聊天界面里觉得模型“记得刚才”，通常是因为你的应用重新发送历史，或者 API 服务端替你保存并重新注入历史。这一课把 message role、instruction 和 conversation state 拆清楚。

1

先看最容易误解的一件事：模型本体 ≠ 聊天记录数据库

一次推理结束后，下一次推理仍然需要上下文再次进入模型。
❌ 错误脑图

“我昨天告诉模型我的名字，所以模型自己脑子里永久记住了。”

✅ 更准确

应用/供应商保存了对话状态；下一轮请求时，相关历史再次成为模型输入。

Turn 1
用户 + 指令
→
模型推理
→
保存历史
→
Turn 2
历史 + 新问题
→
再次推理
这一区别会直接决定后面三个工程问题：context window 会增长、历史会花 token、敏感数据是否由 provider 存储要明确。
2

Messages 不是“几段文字”，而是带角色的上下文块

角色告诉模型：这段内容是谁说的、它应该被怎样理解。
Instruction
系统/开发者侧规则

定义任务、边界、风格、输出要求。不同 provider 的字段名不同，但概念相近。

User
用户当前输入

用户问题、需求、文件内容或其他输入。

Assistant
模型之前的输出

多轮对话中，它本身也是后续上下文的一部分。

Tool / Event
工具调用和结果等结构化上下文

后面 Tool Calling 课会专门拆。不要把所有东西都硬塞成 user 文本。

不要死背某一家 SDK 的 role 名称。OpenAI、Anthropic、Gemini 在顶层 instruction、message block、conversation handle 上的 API 形状不同；面试真正要懂的是“指令、用户输入、模型历史、工具事件如何组成上下文”。

4

Interactive：同一段聊天，Stateful 和 Stateless 到底差在哪？

点击增加轮次，再切换模式，看“谁负责保存历史”。
CHAT UI

Stateless：你的应用自己保存 history，并在每轮请求重新发送相关上下文。
Stateful：服务端保存 conversation/interaction state，你提交新输入 + 某个关联 ID；服务端再把历史恢复给模型。
5

Stateful 更方便，但不是“免费记忆”

历史仍然存在，仍然会受上下文、存储、隐私和供应商语义影响。
Stateful 的好处

少传大量历史、调用代码更简单、provider 可以维护内部事件/工具/推理连续性。

Stateful 的代价

依赖 provider 的存储/保留策略；迁移供应商更复杂；对话状态生命周期需要管理。

Stateless 的好处

上下文完全由自己控制；更容易存自己数据库、做审计、跨 provider 迁移。

Stateless 的代价

需要自己管理 history、裁剪、工具事件和特殊 reasoning metadata；请求体会越来越大。

真实工程里经常混合：短会话使用 provider state；关键业务记录仍写入自己的数据库；真正长期记忆则做独立 memory / retrieval 系统。不要把 provider conversation state 当成长期用户记忆。
6

Instruction 不应该每轮随意和用户文本混成一坨

把稳定规则和动态任务分离，才能调试、版本化和做 eval。
稳定 Instruction
你是科研助手。
引用不确定时明确说明。
回答使用中文。

属于产品行为，应版本化。

7

Conversation history 不是越多越好

第 03 课才正式讲 token/context，但现在先建立一个关键直觉。
历史越来越长
→
输入 token 增加
→
成本 / latency
→
噪声也增加
→
需要 context strategy
真正的 Context Engineering 不是“把所有旧消息都塞回去”，而是决定：哪些 instruction 永远保留、哪些最近对话保留、哪些旧信息摘要、哪些根本丢掉。
8

Research Assistant v1.2：加 Conversation Manager

不要让所有业务代码直接操作一个无限增长的 messages list。
from dataclasses import dataclass, field

@dataclass
class Conversation:
    instructions: str
    messages: list[dict] = field(default_factory=list)

    def add_user(self, text: str) -> None:
        self.messages.append({"role": "user", "content": text})

    def add_assistant(self, text: str) -> None:
        self.messages.append({"role": "assistant", "content": text})

    def context(self) -> list[dict]:
        return self.messages[-8:]  # 临时策略；03 会升级
练习

为什么 messages[-8:] 只能算临时策略，而不能作为真正的 context management？

参考

因为“8 条消息”不等于固定 token 数，也不考虑重要性；一条消息可能是 5 个字，也可能是整篇论文。真正策略要看 token budget、信息优先级、摘要和当前任务相关性。
