LLM 09 · Research Assistant v1.9

生产系统不是“永远调用最强模型”。
它是在约束下选最合适的模型。

真实产品同时被能力、质量、延迟、成本、可靠性、上下文、地区与供应商故障约束。Router 的工作不是猜“谁最聪明”，而是先淘汰不能做任务的模型，再在可行集合里做可解释选择。

1

先把“选模型”从排行榜思维里救出来

一个模型全局更强，不代表它在每个请求上都是最优。
简单分类

500 ms 内完成比多 2% 准确率更重要，便宜快速模型可能更合理。

高风险科研结论

复杂推理和证据一致性更重要，允许更高延迟与成本。

图片 + Tool

先要支持视觉与工具调用；不支持的模型质量分再高也没资格参赛。

Router 的第一条规则：先做 capability gate，再做 optimization。不能让加权分数把“根本不支持图片”的模型选去做视觉任务。

5

Latency 也不能只看平均值

用户被 p95/p99 卡顿折磨，而不是被“平均 1.2 秒”安慰。
指标回答什么问题
TTFT用户多久看到第一块输出？
p50典型请求有多快？
p95 / p99尾部慢请求有多糟？
timeout rate有多少请求直接跨过你的 SLO？
一个模型 p50 很快但 p99 经常 30 秒，和一个稳定 3 秒的模型，是完全不同的产品体验。
6

Fallback：失败后换模型，不等于“继续重试直到成功”

你需要知道为什么失败，以及换模型后语义会不会变。

适合 fallback

provider 5xx、区域故障、明确限流、模型暂时不可用。

不该盲目 fallback

schema 设计错、prompt 本身有 bug、工具权限不允许、用户请求本来就不合法。

隐藏风险：备用模型可能不支持同样的 tool/schema/multimodal 语义。Fallback 之前要重新 capability gate，而不是只替换 model name。
7

可靠性设计：Circuit Breaker 比“每个请求都撞墙”聪明

当一个 provider 明显故障时，暂时停止继续打它。
连续失败
→
Circuit OPEN
→
暂时绕开
→
冷却时间
→
Half-open 探测

这和 Python 06 的 retry 是不同层次：retry 处理单次调用；circuit breaker 处理“这个依赖整体现在可能不健康”。

Research Assistant v1.9：Router 输出“决策”，不直接藏起来

可解释路由以后才能调试和做 eval。
decision = router.route(RouteRequest(
    needs_tools=True,
    needs_vision=False,
    quality_priority=0.8,
    latency_priority=0.5,
))

print(decision.model)
print(decision.reason)
print(decision.fallbacks)
日志至少记录：候选集合、淘汰原因、最终模型、fallback chain、实际 latency/usage/error。否则 Router 出问题时你只看到“回答变差了”。
