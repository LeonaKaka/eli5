LLM
LLM 10 · Research Assistant v2.0

“我改完感觉更好了”
不是工程验收。

LLM 系统最危险的地方之一，是你改了 prompt、model、context、tool 或 Router 后，某些样例变好，另一些悄悄变坏。最后一课建立完整闭环：Eval Set → Error Analysis → Regression Gate → Deploy → Production Trace → 再 Eval。

1

为什么普通 unit test 不够？

因为 LLM 质量通常不是一个固定字符串等式。
确定性代码
assert add(2, 2) == 4

输入和输出关系明确。

LLM 输出
answer = summarize(paper)
# 合理答案可能有很多种措辞

真正要测的是事实、格式、引用、规则和任务成功率。

所以测试对象要从“逐字相同”升级成“行为是否满足可评价标准”。
2

Eval Set：先保存真实任务，不要只保存漂亮 Demo

好的 eval set 应该包含典型、困难、边界和失败样例。
Happy path

最常见用户任务，确保基础能力不退化。

Hard cases

长上下文、歧义问题、复杂推理、低质量文件。

Safety / Edge

Prompt injection、坏 Tool 参数、敏感数据、provider failure。

EvalCase(
    id="citation-017",
    input="总结这篇论文并引用证据页码",
    expected={"must_cite": True},
    tags=["citation", "pdf", "critical"],
)
不要只挑模型容易答对的题。真正有价值的是“你的产品曾经失败过、未来还可能失败”的样例。
3

四类 Eval，不要迷信单一 Judge

不同问题适合不同评价方式。
方式适合注意
DeterministicSchema、字段、引用存在、Tool 权限最稳定，优先能写规则的部分
Reference-based分类、抽取、已知答案 QA需要可靠 reference
Rubric / LLM Judge摘要完整性、风格、开放回答Judge 也会偏，需要校准
Human Review高风险、难定义、体验判断贵，但常是最终真值来源
能用确定性规则的地方，不要为了“AI 味”强行用 LLM Judge；开放质量问题再用 rubric/judge，并抽样做人审校准。
4

Interactive：Regression Gate

模拟一个候选版本在不同 slice 上的变化，看看它该不该发布。所有数字仅用于教学。
SliceBaselineCandidateΔGate
关键：平均分上涨不能掩盖 critical slice 退化。比如整体更好，但 Tool 权限测试从 100% 掉到 95%，仍然应该挡住发布。
5

Error Analysis：Eval 只告诉你“哪里差”，分析才告诉你“该修什么”

不要看到总分下降就立刻再改 Prompt。
Retrieval
  • 没取到证据
  • 取错文档
  • 排序错误
Retrieval

证据没进 context。

Generation

证据有了但回答仍错。

Tool

选错动作、参数或执行失败。

Product

延迟、成本、UI、流程本身失败。

这一步非常重要：RAG 检索错了，继续改 system prompt 通常治标不治本；Tool 权限错了，更不应该靠“请模型小心一点”修。
6

线上到底用了哪一版 instruction，必须能追溯。

    version="v12",
    template_sha="9c21...",
    created_at="...",

7

Production Trace：真实用户是你最大的隐藏测试集

但生产数据要经过隐私与采样策略，不是“所有聊天永久保存”。
Request

task、model、prompt version、context ids。

Execution

latency、usage、tool calls、retry、route decision。

Outcome

status、user feedback、eval tags、error category。

{
  "trace_id": "tr_91d",
  "prompt_version": "research-v12",
  "model": "balanced",
  "route_reason": "vision+tools",
  "latency_ms": 2840,
  "tool_calls": ["search_papers"],
  "status": "completed"
}
没有 trace，你只知道“用户说今天不好用”；有 trace，才可能定位是 model、context、tool、provider 还是产品流程。
8

Production Safety：安全不是最后加一个 moderation 开关

前 9 课的每个边界都有自己的安全问题。
Prompt / Context

Prompt injection、不可信文件内容、系统指令泄漏。

Tools

权限、审批、参数验证、side effects、idempotency。

Data

PII、secret、retention、日志脱敏、删除链路。

Models / Providers

数据处理策略、地区、fallback 语义、供应商故障。

安全的核心是分层：模型输出不可信、工具输入要验证、危险动作要授权、文件内容是不可信数据、日志不能把 secret 全量抄进去。
9

完整开发闭环

这就是“Evaluation-driven development”真正落到工程里。
真实失败样本
→
加入 Eval Set
→
改 Prompt / Model / RAG / Tool
→
跑 Eval
→
Regression Gate
→
Deploy
→
Trace
每遇到一次有价值的线上失败，都应该问：能不能把它变成永久回归测试？如果可以，这次事故才真正让系统变强。
10

Research Assistant v2.0：终于从 Demo 变成“可评估系统”

v2.0 的定义不是功能更多，而是每个关键行为都有契约、观测和回归保护。
Context
→
Router
→
Model
→
Tool / Files
→
Structured Result
→
Trace + Eval
report = suite.evaluate(candidate)

gate = RegressionGate(
    minimum_score=0.80,
    max_regression=0.03,
    critical_tags={"tool-permission", "citation"},
)

if not gate.accept(report):
    raise DeploymentBlocked(report.failures)
