Context Window 不是“记忆容量”。
它更像模型这一次工作的桌面。

上一课知道了历史必须重新进入模型。这一课解决真正的工程问题：桌面有限时，instruction、历史、论文证据和输出空间怎么分？真正的 Context Engineering 不是把能找到的东西全部塞进去。

1

Token 是模型真正处理的“文字碎片单位”

不是字数，也不是单词数；具体切法取决于 tokenizer / model。
字符人看到的文本单位
Token模型输入输出的计量单位
Context本次推理能看到的 token 集合
Usage真实请求后 provider 返回的计量
不要写死“1 token = 几个汉字”。语言、标点、代码、模型 tokenizer 都会改变结果。做预算可以估算，做计费/监控要优先读取真实 usage。

Interactive：32k 的“桌面”到底怎么被吃掉？

这个 32k 只是教学窗口，不代表某个具体模型。拖动四块预算，看什么时候爆窗。

关键：输入和输出不是两个毫无关系的世界。很多接口都有总上下文/输出上限约束；即使窗口够大，也应给输出和系统开销留余量。

上下文超了，最差的做法是“从最前面机械砍掉”

因为最前面可能恰好是稳定规则，最中间可能恰好是关键证据。

Context Engineering 的核心：按任务价值分配注意力预算。常用工具包括 recent-window、摘要、retrieval、metadata filter、结构化 state，而不是“历史越完整越专业”。
4

“大 Context Window”不等于“无限可靠记忆”

容量变大解决的是“装得下”，不自动解决“哪些内容最重要”。
❌ 装得下 200 页

所以把 200 页全塞进去，模型一定能稳定抓住第 137 页的一句关键条件。

✅ 更好的工程思维

窗口大提供了更多选择空间；仍要做相关性筛选、结构化组织、引用定位和 eval。

5

Prompt / Context Caching 到底缓存了什么？

它通常是在重复请求中复用稳定前缀的计算/计费优势，不是给模型新增“永久记忆”。
Request 1
稳定前缀
新输入
Request 2+
可复用前缀
新输入
完全不复用

token·request 的输入工作量

潜在可复用部分

token·request 的重复前缀

缓存不是“少算 context window”。稳定前缀仍然属于模型这次输入的一部分；具体命中、价格、保留时间、最小前缀长度由 provider/model 决定，要读当前文档和 usage。
6

让 Cache 命中的写法，通常也更利于工程维护

稳定的放前面，频繁变化的放后面。
更稳定的前缀
instructions
schema / tool definitions
long reference handbook
----------------------
current user question

稳定块不频繁改顺序，重复请求更容易复用。

很难复用
timestamp
random request id
user question
instructions
randomized examples
...

每次前面都变，后面的稳定内容也可能无法形成相同前缀。

这不是要求你为了 cache 牺牲正确 prompt 结构，而是提醒：稳定系统规则 / tool schema / 长文档若能保持稳定顺序，通常同时改善版本管理和缓存机会。

Research Assistant v1.3：ContextBuilder 不再等于 messages[-8:]

把“什么值得进入模型”变成一个可测试的模块。
class ContextBuilder:
    def build(self, state, evidence, budget):
        blocks = []
        blocks.append(self.instructions(state))
        blocks.extend(self.relevant_evidence(evidence))
        blocks.extend(self.recent_messages(state))

        while self.estimate_tokens(blocks) > budget:
            blocks = self.compress_low_priority(blocks)

        return blocks
输入

任务 state、对话、检索证据、token budget。

策略

优先级、相关性、摘要、裁剪、输出预留。

观测

估算 token + provider 返回真实 usage。

练习

当前任务是“比较 A/B 两篇论文实验方法”，历史里有 30 轮聊天、5 篇论文全文和一个固定输出 schema。你会先删/压缩哪一类？为什么？

参考

先压缩与当前比较无关的旧聊天和低相关论文；固定 schema/instructions 与 A/B 的直接证据优先保留。真正决策应由相关性 + token budget 驱动。
