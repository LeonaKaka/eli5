Tool Calling 最重要的事实：
模型不会真的“执行 Python”。

模型做的是：根据你提供的 tool schema，生成一个“请应用调用这个工具，并使用这些参数”的结构化请求。真正联网、查数据库、删文件、发邮件的，永远是你的应用代码。

1

先把“模型会用工具”的魔法拆掉

Tool Calling 是一个两段式协议：模型负责决定，应用负责执行。
LLM 的职责
tool_call:
  name: search_papers
  arguments:
    query: "RAG evaluation"
    top_k: 5

它只产生“动作请求”。

→
你的应用的职责
args = SearchArgs.model_validate(call.arguments)
result = await search_papers(**args.model_dump())

验证、授权、真正执行，再把结果返回模型。

危险错觉：“模型调用了 delete_file，所以文件是模型删的。”更准确地说，是你的程序看见模型提出 delete_file 请求后，选择了执行它。安全边界必须写在应用层。
2

Tool Schema 是给模型看的 API 菜单

description 决定“什么时候用”，parameters 决定“怎么填参数”。
{
  "name": "search_papers",
  "description": "Search academic papers relevant to a research question",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string"},
      "top_k": {"type": "integer", "minimum": 1, "maximum": 20}
    },
    "required": ["query"]
  }
}
名字

短、稳定、动作导向：search_papers、get_weather。

Description

不仅解释“它是什么”，还要告诉模型适用边界和不适用场景。

Parameters

字段越模糊，模型越容易乱填；把类型、范围和必填项机器化。

Tool description 不是营销文案。如果两个工具描述高度重叠，模型会更难稳定路由。真正项目里要用 eval 看“选错工具率”，而不是凭感觉改 prompt。

4

Call ID 为什么重要？

一个 response 可能有多个工具调用，结果必须准确回到对应调用。
tool_call
call_A7f
→
search_papers()
→
tool_result
call_A7f
→
LLM 继续推理

不要仅凭工具名关联结果：同一轮里模型可能两次调用 search_papers，参数完全不同。Call ID 是协议层关联键，也是日志和 trace 的好入口。

ToolCall(
    id="call_A7f",
    name="search_papers",
    arguments={"query": "RAG", "top_k": 5},
)

ToolResult(
    call_id="call_A7f",
    ok=True,
    output={"papers": [...]},
)
5

安全不是“在 Prompt 里告诉模型不要乱来”

真正权限控制必须由应用自己做。
🟢 Read-only

搜索论文、读天气、查询数据库。通常可以自动执行，但仍需参数/资源范围限制。

🟠 Side effect

发邮件、创建日历事件、写数据库。常常需要明确规则、幂等和用户确认。

🔴 Destructive / Sensitive

删除数据、转账、修改权限、执行任意 shell。默认禁止或强审批。

Prompt Injection 进入 Tool Calling 后危险性会升级。网页里的恶意文字如果能诱导模型调用“发送 secret”工具，而应用又无权限层，问题就从“答错一句话”升级成真实副作用。
Untrusted content
→
LLM proposes action
→
Policy / Approval
→
Only then execute
6

Tool Error 也应该是“数据”，不是一律崩异常

模型需要知道工具失败了，才能决定换路、重试或解释。
{
  "call_id": "call_A7f",
  "ok": false,
  "error": {
    "type": "timeout",
    "message": "search service timed out",
    "retryable": true
  }
}
Invalid args

不执行，告诉模型参数哪里不符合 schema。

Transient failure

应用可有限 retry，或把 error result 返回模型做 fallback。

Permanent / denied

不要让模型无限请求同一动作；明确告诉它“此路不可用”。

不要把所有工具异常都原样喂给模型。内部 stack trace、数据库 DSN、文件系统路径可能包含敏感信息。返回的是“模型需要做下一步决策所需的最小错误结构”。
7

一次 Tool Call 和真正 Agent Loop 的区别

Tool Calling 是能力；Agent 是让模型在状态和停止条件里反复决定下一步。
LLM判断下一步
Tool Call请求动作
Execute应用执行
Observation结果回模型

如果只允许一次搜索然后回答，这是一个受控的 tool-assisted workflow；如果模型可以连续搜索 → 读文件 → 算数 → 再搜索，直到满足停止条件，就开始接近真正 Agent Loop。

后面的 Agent 能力线会深入：state、max steps、checkpoint、memory、human-in-the-loop、guardrails。现在先把“单次/少量受控 Tool Calling”学扎实。
8

并行 Tool Calls：能并行，不代表都该并行

独立读操作可以并行，有依赖或副作用的动作要谨慎。
两个调用是否适合并行原因
search_arxiv(A) + search_web(A)通常可以互相独立、都是读操作
create_order() + charge_card()通常不该盲并行存在业务依赖与副作用
read_file(A) + read_file(B)通常可以独立 I/O
delete_old() + migrate_data()危险顺序和失败恢复都很关键
这正好复用了 Python 05 的 async 思维：并发是执行策略，不是模型“更聪明”。应用层必须决定哪些 call 可以安全并发。

Research Assistant v1.7：ToolRegistry + ToolExecutor

模型只看规范化 tool spec；真正 Python 函数藏在 registry 后面。
registry.register(
    ToolSpec(
        name="search_papers",
        description="Search academic papers",
        args_model=SearchArgs,
        permission=Permission.READ_ONLY,
    ),
    handler=search_papers,
)

call = ToolCall.model_validate(model_output)
result = await executor.execute(call)
