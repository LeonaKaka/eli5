Streaming 不会让模型“更快算完”。
它让用户更早看到第一块结果。

普通请求像“整篇回答写完再一次性交卷”；streaming 像“模型一边生成，服务一边把增量事件推给你”。这一课重点不是某家 SDK 的参数，而是TTFT、event stream、delta、取消、partial failure这些真实工程问题。

1

先分清两个“快”

用户觉得快，和模型真的更早完成，不是一回事。
TTFT · Time To First Token

从用户发送请求，到第一块可见输出出现。它决定“有没有立刻响应”的体感。

Total Latency

从请求开始，到完整回答全部结束。Streaming 通常主要改善前者，不保证缩短后者。

请求发出
→
排队 / Prefill
→
第一个 delta
TTFT
→
持续生成
→
done
Total
常见误区：“开了 stream，所以推理速度变快。”不一定。你只是不用等完整 response 才开始渲染。

3

网络上传的不是“一个越来越长的字符串”

更准确的心智模型是：服务端持续发送结构化事件，客户端按事件类型处理。
request
→
response.created
→
text.delta × N
→
response.completed
async for event in client.stream(...):
    if event.type == "text.delta":
        ui.append(event.delta)
    elif event.type == "completed":
        finalize(event.response)

具体事件名会因 provider/API 变化，但共同逻辑一样：创建 → 多个增量 → 可能的工具/状态事件 → 完成或错误。

坏实现：“只要收到任何字符串就 append”。以后一旦同一 stream 里混入 usage、tool call、error、metadata，你的 UI 就会把协议事件当正文。
4

SSE、WebSocket、普通 HTTP：什么时候用哪个？

别把“实时”自动等同于 WebSocket。
方式适合直觉
普通 HTTP短回答、后台任务、一次性返回写完再交卷
SSE / HTTP streaming服务端持续往浏览器推文本/事件单向直播字幕
WebSocket双方频繁双向实时交互长期双向对讲
大多数“模型回答逐字显示”场景，单向服务器→客户端流已经够用。后面 FastAPI 课会把 SSE/streaming response 真正接到前端。
5

取消不是“浏览器不显示了”

真正的取消要沿调用链往下传播，尽量停止无意义工作。
用户点 Stop
→
前端 abort
→
后端收到 disconnect / cancel
→
取消 provider stream
→
记录 cancelled
只停止 UI 渲染

用户看不到后续内容，但后端和模型可能还在继续生成，成本与资源仍然消耗。

传播取消

尽量关闭下游 stream、停止后处理，并把这次请求标记为 cancelled 而不是 completed。

Partial output 的规则

可以作为 UI 临时内容，但不要在没有完成信号时直接写入“最终答案”、缓存、向量库或业务状态。

6

Streaming 失败，比普通请求多一个尴尬状态

已经吐出一半答案，然后网络断了。
0 token 时失败

像普通请求失败：可明确提示重试。

输出一半后失败

用户已经看到部分内容，需要标记“不完整”。

完成事件后失败

要区分 response 已完成，还是只是 UI 后处理失败。

设计原则：状态机最好至少区分 pending / streaming / completed / cancelled / failed，不要只用一个 is_loading 布尔值。
7

Streaming 与 Structured Output 有天然张力

这正好引出下一课。
自由文本 Streaming

每个 delta 都可以立即展示，半句也有视觉价值。

JSON / Schema

前半截 JSON 往往根本不是合法对象。业务代码通常要等完整结构后再 validate。

# UI 可以一边显示生成过程
partial_text += delta

# 但业务对象要等 complete 后再验证
if event.type == "completed":
    result = PaperSummary.model_validate(response.output)
所以“流式展示”和“结构化最终结果”常常是两条消费路径：前者服务用户体验，后者服务程序逻辑。

Research Assistant v1.5：把 Stream 变成显式状态机

项目里不让 UI 直接依赖 provider 的所有原始 event。
class StreamState(str, Enum):
    PENDING = "pending"
    STREAMING = "streaming"
    COMPLETED = "completed"
    CANCELLED = "cancelled"
    FAILED = "failed"

@dataclass
class StreamResult:
    text: str = ""
    state: StreamState = StreamState.PENDING
