LLM 06 · Research Assistant v1.6

人能看懂“差不多对”的回答。
程序需要字段、类型和失败边界。

如果下游要把模型结果写数据库、画图、调用 API 或决定下一步，“请输出 JSON”远远不够。这一课把自由文本、JSON、Schema、Pydantic 和业务 validation 分层拆开。

1

先看程序为什么讨厌自由文本

同一个意思，人类能容忍十种写法；代码不能靠猜。
给人看的回答
这篇论文很值得读。
我会给 0.91 分。
标签：RAG、evaluation

人类马上理解。

给程序消费
{
  "score": 0.91,
  "tags": ["RAG", "evaluation"],
  "worth_reading": true
}

字段名、类型、结构明确，才能可靠进入下一步。

Structured Output 的本质不是“让回答更漂亮”，而是把自然语言边界变成软件接口边界。
2

四个层级，不要混成一句“模型会输出 JSON”

每上一层，程序能依赖的东西更多。
① 自由文本

格式完全靠提示和运气。

② JSON 语法

至少能 JSON.parse，但字段可能仍然错。

③ JSON + 错类型

语法合法，但业务契约不满足。

④ Schema / Pydantic

字段、类型、范围都能验证。

JSON 合法 ≠ 数据正确。{"score":"很高"} 是完全合法的 JSON，但如果业务要求 0–1 float，它仍然是坏数据。
3

Interactive：同一份“论文评分”经过四层约束

切换模式、改内容，再运行验证。
点击运行。
你应该形成这个习惯：先问“下游代码到底依赖什么字段和类型”，再设计输出 schema，而不是先让模型自由发挥，最后再写一堆字符串修补。
4

Pydantic 为什么在这里又回来了？

Python 02 学的是边界 validation；现在它正式接上 LLM 输出。
from pydantic import BaseModel, Field

class PaperAssessment(BaseModel):
    title: str
    score: float = Field(ge=0, le=1)
    tags: list[str]
    worth_reading: bool

assessment = PaperAssessment.model_validate(raw_output)
模型 output
→
JSON / structured object
→
Pydantic validate
注意层次：Provider 侧的 strict/schema-constrained generation 可以提高“生成时符合 schema”的概率或保证；应用侧 Pydantic 仍然值得保留，因为它是你自己的最终业务边界。
5

Structured Output 不能替你验证“事实真不真”

Schema 只保证形状，不保证内容事实。
Schema 能保证

score 是数字、tags 是数组、字段存在。

Schema 不能保证

论文年份真的对、作者真的存在、引用真的支持结论。

还需要

业务规则、retrieval evidence、数据库校验、eval。

{
  "title": "不存在的论文",
  "score": 0.99,
  "tags": ["RAG"]
}

这份数据可以 100% 通过 schema，但事实仍可能完全错。

常见误区：“上了 structured output，hallucination 就解决了。”没有。你只解决了格式不确定性的一部分。
6

失败路径要设计：Refusal、Invalid、Missing、Truncated

不是只有“成功 JSON”和“程序崩了”两个状态。
Refusal / Safety

模型明确不执行任务。它不是 schema parse error。

Invalid output

provider 没有严格约束，或兼容层失败，输出不符合契约。

Truncated

输出预算/连接问题导致结构不完整。

不要把 refusal 强行塞成业务对象。

如果模型拒绝回答，应用层应该显式处理 refusal/error 状态，而不是伪造一个 PaperAssessment(score=0)。

7

Structured Output 和 Tool Calling 不是同一件事

下一课会深入，但现在先把边界钉牢。
Structured Output

“请把这次回答变成一个满足 schema 的数据对象。”

{"score":0.9,"tags":[...]}
Tool Calling

“模型请求应用执行一个动作，并给出结构化参数。”

search_papers({"query":"RAG"})
共同点：都有 schema / 参数结构。区别：Structured Output 是结果；Tool Call 是动作请求。真正动作仍由你的应用执行。

Research Assistant v1.6：把“最终答案”拆成人类视图和机器视图

同一次模型能力，可以同时服务 UI 和业务逻辑。
class PaperAssessment(BaseModel):
    title: str
    score: float = Field(ge=0, le=1)
    tags: list[str]
    summary: str

class StructuredResult(BaseModel):
    assessment: PaperAssessment | None = None
    refusal: str | None = None
    completed: bool = True
