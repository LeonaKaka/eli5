LLM 04 · Research Assistant v1.4

参数不是“质量滑杆”。
它们是在不同方向上改变模型行为。

很多教程把 temperature、max tokens、reasoning effort 写成参数表。真正工程问题是：什么任务需要稳定、什么任务需要发散、什么任务值得花更多推理预算，以及这些设置怎样影响延迟、成本和可复现性。

1

先拆一个最常见误区：“参数越大，模型越聪明”

不同控制项改变的是不同维度。
随机性 / Sampling

影响候选 token 的选择分布，更多是“发散 vs 稳定”。

Reasoning Budget

某些模型可分配更多内部推理计算，更像“多想一会”。

Output Budget

限制最多能写多少，不等于允许想得更深。

Prompt / Context

告诉模型任务和证据；往往比乱调参数更重要。

重要：不同 provider / model 支持的控制项不一样。有些 reasoning 模型会限制或忽略部分传统 sampling 参数。项目代码应该读取当前模型文档，不要假设所有参数永远通用。
2

Interactive：同一个“旋钮组合”不适合所有任务

切换任务类型，观察推荐方向；右侧分数只是教学 trade-off，不是模型 benchmark。

预计任务质量
预计延迟
预计成本
正确用法：先根据任务选择模型和 prompt，再用 eval 找到参数 sweet spot。不要靠“temperature 0.3 是最佳实践”这种没有任务上下文的固定数字。
3

Temperature / top-p：控制“怎么采样”，不是“知识有多少”

先理解直觉，不死背某家 API 默认值。
低随机性

更偏向高概率候选，适合抽取、规范输出、稳定改写等任务。

↔
高随机性

增加多样性，适合探索、命名、创意方案；也可能更飘。

Temperature

改变概率分布的“尖/平”程度，是最常见的随机性直觉。

top-p

只从累计概率达到某阈值的一组候选里采样；也是控制发散的方式。

坏习惯：temperature 和 top-p 两个都随手乱调，然后发现结果变化却不知道是谁造成的。除非你有明确理由，否则优先固定一组策略并用 eval 比较。
4

“temperature = 0”也不等于数学意义上的确定函数

工程上不要把 LLM 当作完全 deterministic 的数据库查询。

测试策略：不要写“输出必须等于这一整段字符串”的脆弱测试。更常见的是验证 schema、关键事实、分类标签、引用、规则满足度，再配合 eval dataset。
5

Reasoning effort：更像“给难题更多计算预算”

它和“回答写得长”不是同一件事。
高 reasoning 可能值得

复杂代码调试、多约束规划、数学推理、复杂科研比较。

高 reasoning 常常浪费

格式转换、简单分类、固定字段抽取、很短的模板回复。

❌ “输出 5000 token”

只是允许模型写更多字，不保证内部推理更充分。

✅ “给复杂任务更高 reasoning budget”

某些模型/API 会单独暴露推理控制；代价通常是更多延迟/计算。

面试要点：Reasoning control 是模型/供应商特性，不应伪装成所有 LLM 都有一个统一字段。你的 provider abstraction 要允许 capability differences。
6

Max output：是“刹车线”，不是写作目标

过小会截断，过大则可能浪费预算；最好同时用 prompt/schema 控制内容。
太小

答案中途被截断，JSON/代码甚至不完整。

合理

给任务足够空间，同时让 prompt 约束格式与长度。

无限放大

不代表模型更聪明，只增加潜在输出和成本上限。

第 03 课的 Context Budget 和这里直接相连：你给输出留多少空间，会影响还能塞多少 instruction/history/evidence。
7

参数调优的正确顺序：先 Error Analysis，再动旋钮

“回答不好”可能根本不是参数问题。
1
看失败样本

到底是缺证据、任务没说清、模型能力不够，还是输出太随机？

2
确定最可能原因

Context / Prompt / Model / Parameters / Tool / Parsing 分层定位。

3
一次只改一个主变量

否则无法知道变好来自哪里。

4
跑同一套 Eval

比较质量、延迟、成本，不靠三次手测“感觉更好”。

8

Research Assistant v1.4：把 GenerationConfig 变成显式配置

不要在十个调用点散落不同的 magic numbers。
from dataclasses import dataclass

@dataclass(frozen=True)
class GenerationProfile:
    name: str
    randomness: str
    reasoning: str
    max_output_tokens: int

EXTRACT = GenerationProfile(
    name="extract",
    randomness="low",
    reasoning="low",
    max_output_tokens=1200,
)

RESEARCH = GenerationProfile(
    name="research",
    randomness="low",
    reasoning="high",
    max_output_tokens=4200,
)
为什么这里先用语义层而不是直接写 provider 参数？因为不同 provider 对 randomness/reasoning 的字段和支持范围不一样。Adapter 再把语义 profile 映射成当前 provider 支持的参数。
