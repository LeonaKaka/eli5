Agent 07 · Research Assistant v3.7

Agent 跑十分钟后进程崩了。
真正的问题不是“怎么重启”，而是：哪些动作能重放，哪些绝对不能。

长任务、审批暂停、外部 API 和副作用一旦出现，内存里的 while-loop 就不够了。Durable Execution 要把关键状态写成 checkpoint，并明确区分 PREPARED / IN_FLIGHT / COMMITTED。但 checkpoint 也不会凭空给你 exactly-once：最危险的是“外部动作已经成功，进程却还没来得及记下来”。

1

最危险的 crash window 在哪里？

副作用和本地状态更新不是同一个原子事务。
1 · PREPARED

已经保存“准备执行 send_message”，但 handler 还没开始。

2 · IN_FLIGHT

外部系统可能已经发送成功，但 COMMITTED checkpoint 还没写下。

3 · COMMITTED

结果已经持久化，恢复时应复用 result，而不是再执行一次。

经典事故：邮件已经发出 → worker crash → 恢复逻辑只看到“step 未完成” → 再发一次。单靠 `try/except + retry` 解决不了这个问题。

3

Checkpoint 不等于 Exactly Once

“我有数据库，所以肯定不会重复执行”是危险误解。
状态我们知道什么恢复动作
PREPARED执行尚未开始通常可以 retry
COMMITTED结果已经可靠落盘reuse committed result
IN_FLIGHT结果未知，外部效果可能已发生safe replay / idempotent replay / reconcile
Exactly-once 往往是端到端协议属性。如果下游 API 本身支持 idempotency key，才有机会让“重复请求”被外部系统折叠为同一次业务动作。
4

Replay Safety 要显式建模

不是所有 Tool 都能共享一个 retry 策略。
SAFE

纯读取、幂等查询、不会改变外部状态。模糊窗口里通常可以再跑。

EXTERNAL_IDEMPOTENT

动作有副作用，但下游服务真正使用 idempotency key 去重。

NON_IDEMPOTENT

发消息、扣款、创建不可重复记录等；模糊窗口默认进入 reconcile。

重要

“我生成了一个 idempotency key”不代表外部系统真的尊重它。adapter 必须有真实契约。

5

Retry、Replay、Resume 是三个不同问题

名字混在一起会让恢复逻辑失控。
概念典型场景
Retry一次已知失败，例如明确的 transient timeout，再尝试同一动作
Replay恢复流程重走已经计划过的 action，需要判断是否可能重复副作用
Resume从持久化 checkpoint 继续整条 run，而不是从用户输入重新开始
07 的 `RecoveryDecision` 会先判断 checkpoint，再决定 RETRY / REUSE_COMMITTED / RECONCILE / STOP，而不是所有异常统一 retry。
6

Checkpoint 应该保存什么？

至少要足够回答“恢复时到底准备做哪一个动作”。
DurableCheckpoint(
    id="run-42:send-7",
    action=DurableAction(
        call=ToolCall(...),
        replay_safety="non_idempotent",
        idempotency_key=None,
    ),
    stage="in_flight",
    revision=2,
)
不要只存 `step=7`。恢复时还需要精确动作、参数、replay contract、结果/错误和 revision，否则无法判断该不该重放。
7

Compensation 不是数据库 rollback

真实世界的副作用通常不能时间倒流。
业务补偿

已经创建了一条记录，可以再创建“取消记录”；已经预订资源，可以调用取消接口。

无法完全补偿

邮件已经被人看到、消息已经推送、外部系统已触发后续流程。只能记录、告知、采取新的补救动作。

v3.7 的 `mark_compensated()` 只记录已完成的补偿事实，不假装存在通用“撤销所有 Tool”的魔法 API。

Research Assistant v3.7：DurableActionRunner

代码明确承认“模糊窗口”，而不是假装所有动作都 exactly-once。
checkpoint = runner.prepare(
    DurableAction(
        run_id="run-42",
        action_id="send-7",
        call=call,
        replay_safety=ReplaySafety.NON_IDEMPOTENT,
    )
)

# crash 后
recovery = runner.recovery_decision(checkpoint.id)
# IN_FLIGHT + NON_IDEMPOTENT → RECONCILE
已 COMMITTED 的 action 再 resume 时直接复用 result。这条边界会被测试锁住，防止恢复路径自己制造重复副作用。

面试验收

Durable Agent 最重要的是能解释 crash window。

Agent 调用 `send_email()` 后邮件可能已经成功发送，但进程在写成功 checkpoint 前崩了。该动作没有 idempotency 支持。重启后最合理？
