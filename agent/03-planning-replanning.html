Agent 03 · Research Assistant v3.3

会决定“下一步”还不够。
长任务需要知道哪些步骤依赖哪些步骤，以及什么时候原计划已经失效。

Agent 01/02 已经有循环和硬停止边界。现在处理更长的任务：先建立一个显式 Plan，执行时不断拿 Observation 检查“计划还能不能继续”。关键不是让模型写一份漂亮 todo，而是让计划拥有 step、依赖、状态、revision 和可观察的 replan 原因。

1

为什么只靠“每一步现场决定”会变乱？

局部最合理的动作，不一定服务全局目标。
Reactive only
看到论文 A → 读 A
看到引用 C → 又读 C
看到关键词 D → 再搜 D
...

每一步都似乎合理，但可能一直扩散，没有完成“比较 A/B 方法”这个 objective。

Plan-guided
1. 定义比较维度
2. 找 A/B 方法证据
3. 找关键结果
4. 综合比较

下一动作仍可动态决定，但知道当前是在服务哪个 subgoal。

Plan 的价值是约束搜索空间和提供进度坐标。它不是要求 Agent 从此机械执行最初方案。

3

Plan 应该是结构化对象，而不是隐藏在一段自然语言里

这样 Agent 才知道 step 是否完成、被阻塞、依赖谁。
Plan(
    objective="比较论文 A 和 B",
    steps=[
        PlanStep(id="scope", description="定义比较范围", status="completed"),
        PlanStep(id="search", description="找方法证据", dependencies=["scope"]),
        PlanStep(id="evidence", description="提取关键结果", dependencies=["search"]),
        PlanStep(id="synthesize", description="综合回答", dependencies=["evidence"]),
    ],
    revision=1,
)
依赖关系很重要。如果 `search` 没完成，`evidence` 就不应该被当成 ready step；这比 prompt 里写“请按顺序执行”更可靠。
4

Planning 不是 Workflow：Plan 可以变

固定流程和动态计划的边界要分清。
系统步骤适合
Workflow代码提前定义 A → B → C流程稳定、合规要求强
Agent + Plan先产生 Plan，执行中可根据 Observation 调整开放式调查、复杂搜索、步数不确定
Reactive Agent没有长期计划，只看当前状态选下一动作简单动态任务、短 horizon
别把所有任务都“Plan 化”。如果只有两步固定调用，普通 workflow 往往更简单。
5

Replan Trigger：到底什么情况值得推翻旧计划？

v3.3 把触发条件放进应用侧 `ReplanPolicy`。
Goal changed

用户明确改变 objective，旧计划不再服务新目标。

Assumption invalidated

新证据证明计划依赖的关键假设错误。

Step blocked

权限、数据缺失或外部依赖让当前路径走不通。

No progress

连续多步没有减少未完成目标或增加有效证据。

不该触发

只是来了一个正常 observation，计划仍然有效。

成本

每次 replan 都要付额外模型调用、状态变化和测试复杂度。

6

Plan Thrashing：Replan 太勤也会成为一种死循环

“灵活”不等于每一步都重新规划。
step 1 observation
→ replan v2
step 2 observation
→ replan v3
step 3 small change
→ replan v4
...
问题：Agent 大量时间花在“重新描述计划”，而不是完成计划。生产系统通常需要 replan threshold、minimum progress window 或明确 trigger。
7

Progress 必须可计算，而不是“模型感觉快完成了”

Agent 02 的 no-progress 到这里开始有结构。
Plan progress

completed steps / total steps、blocked steps、ready steps。

Task progress

新增有效 evidence、完成 subgoal 数、未解决约束是否减少。

一个动作执行成功不等于任务有进展。例如连续 5 次 search 都返回不同但无关结果，Tool 都是 `ok=True`，objective 仍然没有前进。
8

保留 Plan Revision，而不是原地覆盖

这样才能解释“为什么最终走成了现在这条路径”。
v1 · 初始计划→v2 · paper A blocked→v3 · 用户改变目标

日志和 eval 应该能知道哪个 revision 产生了哪个 action。如果只保存最后一版 plan，中间为什么绕路、为什么多花 8 个 tool calls 都很难解释。

9

Research Assistant v3.3：Plan + ReplanPolicy

应用判断“计划是否 stale”，planner 才负责生成新 revision。
decision = ReplanPolicy(no_progress_threshold=2).evaluate(
    plan,
    ProgressSignal(
        blocked_step_ids={"search"},
        consecutive_no_progress_steps=0,
    ),
)

if decision.should_replan:
    plan = revised_plan(
        plan,
        steps=new_steps,
        reason=decision.reason,
    )
真实边界：`ReplanPolicy` 不负责“聪明地生成计划”，它只负责判断旧计划是否已经不值得继续。这样 trigger 可以独立测试。
