Agent 09 · Research Assistant v3.9

最终答案对，不代表 Agent 跑得对。
Agent Eval 必须看整条 trajectory。

普通 LLM/RAG Eval 常把最终 answer 当主要对象，但 Agent 中间会选 Tool、Replan、Handoff、审批、恢复。一个 run 可以最后碰巧答对，却重复搜索 6 次、走错 specialist、无意义 replan，甚至绕过审批。因此生产 Agent 必须把 step trace 变成可计算的轨迹指标。

1

先看一个“答案正确但不能上线”的 Agent

final success 只是结果层，不是过程层。
1  TOOL      search(query=A)              ✅
2  TOOL      search(query=A)              ⚠ repeated
3  REPLAN    rewrite same plan            ⚠ unnecessary
4  HANDOFF   send retrieval to writer     ❌ wrong owner
5  TOOL      fetch evidence                ✅
6  FINAL     correct answer                ✅
如果只看 final answer，这个 case 可能记作 PASS。但真实线上它更贵、更慢、更脆弱，而且 handoff 错误很可能在另一条输入上直接变成失败。

关键：这些标签不是“系统天然知道”。`correct / necessary` 应来自 golden cases、确定性规则、人工 review，或一个已经单独验证过的 judge。v3.9 的 evaluator 负责把标签变成可比较指标，不假装自己能自动理解所有 Agent 行为。


3
Agent 的指标要分层
不要把所有行为平均成一个神秘总分。
Task Success
最终 objective 是否完成。必要，但远远不够。
Tool Choice
选了正确 Tool 吗？有没有调用无关工具？
Efficiency
用了多少 action 才完成？多少是多余步骤？
Handoff
是否交给具备正确 capability 的 owner？
Recovery
crash 后是安全 replay、reuse，还是危险盲重试？
Policy
有没有审批绕过、越权、危险副作用等 critical violation？


4
Loop Efficiency：少一步不一定更好，但无意义步骤必须可见
课程 baseline 用 golden optimal action count 做一个简单归一化。
loop_efficiency = min(
    1.0,
    optimal_action_count / actual_action_count,
)
例如 golden case 通常 4 个 action 能完成，candidate 跑了 8 个 action：
loop_efficiency = 4 / 8 = 0.50
这不是普适“最优路径证明”。开放式研究任务可能存在多条合理路径，所以 production eval 应按 task slice 设计 baseline，而不是全局规定“永远 4 步最好”。


5
Critical slice 不能被平均分掩盖
安全/权限类错误通常必须直接 block release。
Baseline
Task success86%
Loop efficiency72%
Approval violations0
Candidate
Task success91% ↑
Loop efficiency79% ↑
Approval violations2 ❌
仍然 BLOCK。“总体成功率更高”不能抵消 side-effect approval regression。前面 LLM/RAG 的 critical-slice RegressionGate 思想，到 Agent 这里同样适用。


6
Trace 应该记录事件，不只是打印日志
以后才能按 run、step、tool、agent、checkpoint 聚合。
TrajectoryStep(
    index=4,
    kind=TrajectoryStepKind.HANDOFF,
    action="supervisor → retriever",
    correct=True,
    necessary=True,
    fingerprint="handoff:retriever",
)
生产 trace 还会带 `run_id / tenant / model / tool / latency / token / cost / plan revision / checkpoint id / approval id`。不要把这些重要字段藏在一整串自然语言 log 里。


7
Error Taxonomy：同样是“任务失败”，修法可能完全不同
先定位层，再优化。
失败层例子更可能修什么
Decision选错 ToolTool schema / routing / prompt / eval set
Planning无意义 replantrigger / progress signal
Execution并行依赖错误ActionGraph / orchestrator
Approval绕过 side-effect gateapplication policy
Recovery重复发送checkpoint / replay safety
Handoff循环转交ownership / cycle guard

线上看到“审批拒绝率突然升高”或“handoff 数翻倍”，应该沉淀成新的 eval slice，而不是只修一条 prompt 后忘掉。


9
Research Assistant v3.9：TrajectoryEvaluator
把 final success 和 process health 分开。
report = TrajectoryEvaluator().evaluate(
    TrajectoryCase(
        id="research-17",
        task_success=True,
        optimal_action_count=4,
        steps=steps,
    )
)

print(report.tool_choice_accuracy)
print(report.unnecessary_step_rate)
print(report.loop_efficiency)
print(report.handoff_accuracy)
print(report.recovery_correctness)
print(report.critical_violation_count)
print(report.healthy)
一个 case 可以 `task_success=True` 但 `healthy=False`。这就是 Agent Eval 和只看 final answer 的根本区别。


10
面试验收
Agent Eval 不应该只回答“用 LLM-as-a-Judge”。
一个 Agent 最终答案正确，但中途绕过了必须审批的发送操作。是否应该因为 final answer 正确而通过？
面试验收：① 为什么 final answer eval 不够？② Tool-choice / unnecessary-step / loop-efficiency 分别看什么？③ critical slice 为什么不能被平均？④ trajectory label 从哪里来？⑤ Offline eval 和 production traces 如何闭环？⑥ 怎么区分 decision/planning/execution/recovery/handoff failure？


最后一课：把这些控制边界放到真正的 API / Queue / Worker / Store 架构里，Research Assistant 收口到 v4.0。
