Agent 04 · Research Assistant v3.4

Memory 不是“把聊天记录都存起来”。
真正难的是：什么值得记、记多久、以后什么时候敢再用。

Agent 一旦跨多个 run 工作，就需要某些信息持续存在。但长期 Memory 本身也是一个高风险输入源：一次错误总结、过期事实或敏感日志如果被持久化，未来每个决策都可能被污染。所以 Memory 工程的核心是分层、写入门槛、来源、作用域、失效和检索策略。

1

先分清四种“记住”

Context、State、Memory 经常被混成一个词。
Working Memory当前 run 的临时状态：最近 observation、当前 plan、未完成 subgoal。
Episodic Memory过去 run 的事件：上次做过什么、哪里失败、哪条路径有效。
Semantic Memory经过验证、可复用的事实或知识，不依赖某次具体 run。
User Memory明确且允许长期复用的用户偏好/约束，必须有清晰来源和作用域。
Working Memory 通常不等于长期存储。Agent 每一步都需要 state，但不代表这些状态都应该跨 run 永久存在。

3

为什么不能把每个 Observation 都写成长期 Memory？

否则 store 很快变成垃圾场。
一次性状态

“本轮第一次搜索超时”“当前 step=3”“刚刚拿到一个临时候选”。

这些应该留在 Working Memory / Trace。

跨 run 价值

“某篇论文的 DOI 与已验证标题对应”“某个稳定工作流在同类任务上成功”。

才可能进入长期 Memory。

长期 Memory 的成本不仅是存储空间，还包括以后每次 retrieval 的噪声、冲突、过期信息和错误先验。
4

Memory Contamination：错误记忆比“没有记忆”更危险

打开污染开关，看一个错误事实如何影响后续计划。
→
污染会放大。Memory → Planning → Query → Retrieval → Generation。越早进入决策链的错误长期先验，影响范围越大。
5

Write Policy：长期记忆至少要问这几件事

v3.4 把写入门槛放到 `MemoryWritePolicy`。
Reusable?

未来 run 真可能再次用到，还是只属于当前任务？

Confidence?

来源是否足够可靠，是否达到持久化阈值？

Verified?

Semantic fact 是否回到可信来源核对过？

Scope?

属于 run、某个 user，还是 workspace？不能默认全局共享。

Sensitive?

secret、隐私和敏感日志不能进入普通 Memory store。

Source?

以后必须知道这条记忆来自哪里，才能验证或失效。

6

Read Policy 也同样重要：不是“搜到 Memory 就塞进 Prompt”

Memory retrieval 本质上又是一层 RAG。
Current objective
→
Memory search
→
Scope / kind filter
→
Relevance + confidence
→
Context
所以前面学过的 retrieval、dedup、provenance、budget、eval 都会重新出现。Memory 不是一个神秘的新模块，而是“带生命周期和权限的长期检索源”。
7

Stale Memory：事实会过期，Memory 必须能失效

“写入成功”不能意味着永远不可变。
store.invalidate(
    "paper-method-v1",
    reason="superseded by corrected primary-source evidence",
)

# search() 默认只返回 active memory
Invalidate

明确标记这条 Memory 不再参与未来检索，同时保留历史。

Overwrite-only

直接覆盖旧值会失去“什么时候、为什么改”的审计信息。

后面 Durable Execution / Observability 会继续用到这种“保留历史状态而不是原地抹掉”的设计。
8

Memory Scope 是权限边界，不只是分类标签

run / user / workspace 不能混用。
Scope典型内容风险
RUN当前任务临时状态不应跨 run 泄漏
USER明确可复用的个人偏好/设置必须避免跨用户读取
WORKSPACE团队共享、已验证的项目知识需要访问控制和版本管理
生产系统里 scope 应参与查询和授权。不能先把全库搜出来，再让模型自己“不要看不该看的”。
9

Research Assistant v3.4：MemoryStore + Write Policy

当前实现是离线 in-memory teaching baseline，验证的是边界，不冒充生产向量 Memory。
result = store.write(
    MemoryWriteRequest(
        id="paper-doi",
        kind=MemoryKind.SEMANTIC,
        scope=MemoryScope.WORKSPACE,
        content="verified DOI → paper title mapping",
        source="primary-paper",
        confidence=0.97,
        reusable=True,
        verified=True,
    )
)

memories = store.search(
    "paper DOI",
    scope=MemoryScope.WORKSPACE,
)
关键：`MemoryStore.write()` 先经过 `MemoryWritePolicy`。Working Memory、敏感信息、未确认 User Memory、未验证 Semantic Memory、低置信度或没有跨 run 价值的内容都会被拒绝。
