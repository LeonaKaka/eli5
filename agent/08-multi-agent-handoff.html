Agent 08 · Research Assistant v3.8

Multi-Agent 不是“多开几个模型一起聊”。
只有职责边界、能力差异和 ownership 真正存在时，拆分才值得。

一个已经有 Plan、Memory、Tool、Approval、Checkpoint 的单 Agent 本身就不简单。拆成多个 Agent 会额外增加 handoff、共享状态、重复上下文、循环 delegation 和协调成本。所以这一课先回答：什么时候一个 Agent 就够，什么时候需要 specialist，handoff 又如何变成可验证 contract。

1

先问：为什么要拆？

“Multi-Agent 更高级”不是工程理由。
场景通常选择
同一模型、同一权限、同一上下文，只是连续做几步一个 Agent + Tools / Plan
明确不同能力：检索、代码执行、写作，且上下文/工具空间可隔离可能值得 Specialist Handoff
多个子任务可并行且有清晰 join contractSupervisor + Specialists 可能有收益
只是为了“模拟公司组织架构”通常只增加 token、延迟和失败面
拆分条件：能力、权限、上下文或并行性至少有一项形成真实边界。否则把同一个问题传来传去只是 orchestration tax。

3

Handoff 必须是 typed contract

不要把整个聊天历史扔给下一个 Agent，再说“你接着做”。
objectivefind evidence for comparison
required capabilities{retrieve}
context refs[query:q1, plan:p3]
expected outputevidence ids + provenance
from → tosupervisor → retriever
return_tosupervisor
HandoffContract(
    id="h1",
    from_agent="supervisor",
    to_agent="retriever",
    objective="find evidence for the comparison",
    required_capabilities={"retrieve"},
    context_refs=["query:q1", "plan:p3"],
    expected_output="evidence ids with provenance",
    return_to="supervisor",
)
Contract 的重点是最小必要上下文。specialist 不需要知道 supervisor 的所有历史，也不应该获得和任务无关的 Tool / Memory / secret。
4

Capability Routing：选“最能做的”还是“刚好能做的”？

通常应该倾向 least-privileged capable specialist。
Supervisor

能力：route + retrieve + write

Retriever

能力：retrieve

Researcher

能力：retrieve + write

任务要求

required = {retrieve} → 优先 Retriever，而不是默认把所有任务都留给权限最大的 Supervisor。

v3.8 的 `SupervisorRouter` 按 capability hard gate 后，再优先选择额外能力最少的 candidate。这既降低动作空间，也符合 least privilege。
5

Ownership 必须唯一且显式

否则两个 Agent 都可能觉得“该我继续”。
owner: supervisor→delegate h1→owner: retriever→complete artifact→owner: supervisor
Owner 是控制面字段。只有当前 owner 能继续 delegate/return；结果完成后通过 `result_ref` 返回，而不是让两个 Agent 并发修改同一段自由文本状态。
6

Interactive：Circular Delegation

一步一步把任务传下去，看到第三次转交为什么必须被 Guard 拦截。
等待操作。
典型坏轨迹：`Supervisor → Researcher → Writer → Researcher → Writer...`。每个 Agent 都有理由把问题“交给更合适的人”，但系统整体没有任何 progress。HandoffGuard 要把 delegation graph 和 budget 当硬边界。
7

共享状态越多，耦合越重

Multi-Agent 不应该默认共享一个无限大黑板。
数据更合理的共享方式
任务目标HandoffContract 中明确 objective
大型检索结果artifact/evidence ref，不复制全部 payload
用户 Memory按 scope + authorization 读取，不自动全共享
中间推理文本通常不需要作为跨 Agent contract
Tool 权限每个 Agent 自己的 allowlist，不能继承 supervisor 全权限
共享最少必要状态，会让 handoff 更便宜、更安全，也更容易 Eval。
8

Multi-Agent 的常见反模式

很多“高级架构”其实只是把一个简单问题拆复杂了。
Role-play agents

没有不同工具/数据/权限，只是 prompt 写“你是研究员”“你是经理”。

Shared free-form chat

所有 Agent 往同一历史里塞文本，ownership 和来源越来越模糊。

Ping-pong delegation

互相认为对方更适合，导致循环转交。

Supervisor bottleneck

所有细节都必须回 supervisor 再转发，token 和 latency 翻倍。

Duplicate work

多个 Agent 不知道彼此已完成什么，重复搜索/调用 Tool。

No eval boundary

只看最后答案，不知道是 routing、handoff 还是 specialist 自己失败。

Research Assistant v3.8：HandoffContract + Coordinator

当前实现验证的是 ownership、capability、cycle 和 contract，不冒充完整 multi-agent runtime。
decision = coordinator.submit(state, contract)

# owner: supervisor → retriever

completed = coordinator.complete(
    state,
    "h1",
    result_ref="artifact:evidence-pack-17",
)

# owner 自动回到 return_to=supervisor
真正重要的不是有几个模型实例。而是任务 ownership 能不能解释、转交 contract 能不能验证、循环 delegation 能不能被拦、结果能不能作为 typed artifact 回来。
