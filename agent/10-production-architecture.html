Agent
Agent 10 · Research Assistant v4.0

Production Agent 不是把 while-loop 放进 FastAPI。
它是一套可持久化、可排队、可取消、可恢复的 Run System。

前九课已经有 AgentLoop、Budget、Plan、Memory、Tool DAG、Approval、Checkpoint、Handoff 和 Trajectory Eval。最后一步不是再加 autonomy，而是把这些能力放进一个明确的生产边界：请求快速入队，Run 状态持久化，Worker 可重启，Queue 可重复投递但旧 revision 不能执行，孤儿 Worker 可被 watchdog 恢复，审批/取消都能跨进程继续。

1

为什么不能直接在 HTTP Request 里跑 20 分钟 Agent？

Web 请求生命周期和 Agent run 生命周期不是同一个东西。
❌ Request-bound Agent
POST /research
  ↓
while agent_running:
  await tool(...)
  await model(...)
  ... 20 min ...

连接断开、进程部署、超时、worker 重启都会让状态非常难处理。

✅ Run-oriented system
POST /runs
  ↓
create RunRecord(status=QUEUED)
  ↓
enqueue START
  ↓
202 + run_id

真正长任务交给 worker；客户端按 run_id 查询/订阅状态。

API 负责创建和控制 run，不负责绑住一个进程直到任务结束。这也是后面 FastAPI 课程会真正接上的地方。

3

RunRecord 是系统真相，不是聊天 history

控制面状态必须独立于模型上下文。
RunRecord(
    id="run-42",
    tenant_id="team-a",
    objective="compare papers",
    status="waiting_approval",
    revision=7,
    budget=RunBudget(...),
    cancel_requested=False,
    current_checkpoint_id="run-42:send-3",
    approval_request_id="approval:call-3",
    owner_agent="supervisor",
)
Conversation/messages 可以重建模型 context，但不能替代 authoritative run state。Worker 到底能不能执行、谁是 owner、是不是已取消，都应该从控制面读取。
4

Revision / CAS：不仅防重复 Job，还防“死而复生”的旧 Worker

claim 得到的 revision 就是一个 optimistic worker token。
START job expected_revision = 5
store revision = 5
→ worker A claim
→ RUNNING revision = 6

同一 START 再投递
expected = 5, current = 6
→ ❌ stale delivery

worker A 卡死
watchdog requeue → QUEUED revision = 7
worker B claim → RUNNING revision = 8

旧 worker A 突然回来：
finish(expected_revision=6)
current = 8
→ ❌ stale worker
只在 claim 时检查 revision 不够。Worker 后续的 `finish / pause_for_approval / checkpoint transition` 也必须携带自己真正 claim 到的 revision，不能偷偷读取最新 revision 后覆盖别人。
5

Cancellation 也是状态机，不是“kill task”

排队中的任务和正在执行副作用的任务不能用同一种取消语义。
RUNNING
→
cancel_requested
CANCELLING
→
Worker safe boundary
→
CANCELLED

如果 Run 还在 `QUEUED / WAITING_APPROVAL`，没有 active worker，可以直接进入 `CANCELLED`。如果已经 `RUNNING`，则先进入 `CANCELLING`，阻止新的动作；Worker 到安全边界后再 `acknowledge_cancel()`。

取消仍然不是 rollback。如果一个不可逆 Tool 已经 IN_FLIGHT，仍要走 07 的 reconcile/compensation；`CANCELLING` 只是阻止系统继续推进新动作，并诚实表示“停止还没有被 Worker 确认”。
6

Approval Resume 必须经过持久化 Run，而不是回到旧进程

等待人 3 小时期间，原 worker 早就应该释放了。
RUNNING
→
Checkpoint
→
WAITING_APPROVAL
→
human approves exact call
→
QUEUED + RESUME
这才是 durable interrupt：暂停状态存在 store 里。批准后产生一个新的 `RESUME` job，由任意健康 Worker claim，而不是试图“唤醒”三小时前那个 Python coroutine。
7

Tenant / Authorization 必须一路跟着 Run

Agent 能力越强，数据边界越不能交给模型自觉。
API boundary

调用者是谁？能创建/取消/审批哪个 run？

RunStore boundary

`run_id` 查询必须同时检查 `tenant_id`，不能只凭 UUID。

Tool boundary

目标资源授权在 ToolExecutor/adapter 层再次检查。

Memory boundary

USER / WORKSPACE scope 参与 retrieval，而不是检索完再让模型忽略。

Artifact boundary

handoff/ref 指向的数据也必须带访问控制。

Trace boundary

日志里避免泄漏 secret，审计身份和动作。

接口可以保留，adapter 必须替换。

手动 requeue_abandoned()worker lease / heartbeat / watchdog + recovery scheduler

Research Assistant v4.0：ProductionControlPlane

把 Agent 从单次函数调用提升成可管理的 Run。
control = ProductionControlPlane()

run = control.submit(
    run_id="run-42",
    tenant_id="team-a",
    objective="compare papers",
)
# run.status == QUEUED

job = control.queue.pop()
claim = control.claim(job)
worker_revision = claim.record.revision

# side effect needs human
waiting = control.pause_for_approval(
    run.id,
    tenant_id="team-a",
    expected_revision=worker_revision,
    approval_request_id="approval:call-9",
    checkpoint_id="run-42:send-9",
)

# human resolved exact call
queued = control.enqueue_resume_after_approval(
    run.id,
    tenant_id="team-a",
    approval_request_id="approval:call-9",
)
# queued.status == QUEUED; a RESUME job now exists

如果 Worker 本身崩掉，则由 lease/watchdog 判定 abandoned 后：

queued = control.requeue_abandoned(
    run.id,
    tenant_id="team-a",
    expected_revision=worker_revision,
    checkpoint_id="run-42:checkpoint-7",
)
# old worker_revision becomes stale immediately
这个模块故意不执行模型本身。它是 control-plane teaching baseline：RunStore / Queue / revision / cancel / watchdog-requeue / approval resume 的 contract。AgentLoop、DurableActionRunner、ApprovalManager、Handoff、Trace 都在 worker/runtime 侧组合。
