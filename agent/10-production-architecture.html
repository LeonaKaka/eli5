Agent
Agent 10 · Research Assistant v4.0

Production Agent 不是把 while-loop 放进 FastAPI。
它是一套可持久化、可排队、可取消、可恢复的 Run System。

前九课已经有 AgentLoop、Budget、Plan、Memory、Tool DAG、Approval、Checkpoint、Handoff 和 Trajectory Eval。最后一步不是再加 autonomy，而是把这些能力放进一个明确的生产边界：请求快速入队，Run 状态持久化，Worker 可重启，Job 可重复投递但不能重复执行旧 revision，审批/取消都能跨进程继续。

1

为什么不能直接在 HTTP Request 里跑 20 分钟 Agent？

Web 请求生命周期和 Agent run 生命周期不是同一个东西。
❌ Request-bound Agent
POST /research
  ↓
while agent_running:
  await tool(...)
  await model(...)
  ... 20 min ...

连接断开、进程部署、超时、worker 重启都会让状态非常难处理。

✅ Run-oriented system
POST /runs
  ↓
create RunRecord
  ↓
enqueue START
  ↓
202 + run_id

真正长任务交给 worker；客户端按 run_id 查询/订阅状态。

API 负责创建和控制 run，不负责绑住一个进程直到任务结束。这也是后面 FastAPI 课程会真正接上的地方。

3

RunRecord 是系统真相，不是聊天 history

控制面状态必须独立于模型上下文。
RunRecord(
    id="run-42",
    tenant_id="team-a",
    objective="compare papers",
    status="waiting_approval",
    revision=7,
    budget=RunBudget(...),
    cancel_requested=False,
    current_checkpoint_id="run-42:send-3",
    approval_request_id="approval:call-3",
    owner_agent="supervisor",
)
Conversation/messages 可以重建模型 context，但不能替代 authoritative run state。Worker 到底能不能执行、谁是 owner、是不是已取消，都应该从控制面读取。
4

Revision / CAS：避免两个 Worker 同时把同一个 Run 往前推

这是比“加一个 Redis lock”更基本的并发思维。
job.expected_revision = 5

store current revision = 5
→ worker A claim
→ update RUNNING revision = 6

同一 job 再投递给 worker B
expected = 5
current  = 6
→ ❌ stale delivery
v4.0 teaching store 用 optimistic revision 检查。生产可以用数据库事务、compare-and-swap、lease 等实现，但语义不能丢：旧 job 不能重新激活已经前进的 run。
5

Cancellation 也是状态，不是“杀掉 Python task 就完了”

外部 Tool 可能已经在执行。
User cancel
→
RunStore
CANCELLED
→
Worker safe boundary
→
Stop next action
取消不能自动撤销现实世界。如果一个不可逆 Tool 已经 IN_FLIGHT，仍然要走 07 的 reconcile/compensation 逻辑；cancel 只是阻止系统继续推进新的动作。

Approval Resume 必须经过持久化 Run，而不是回到旧进程

等待人 3 小时期间，原 worker 早就应该释放了。

这也是“durable interrupt”的真正意义：暂停状态存在 store 里，不依赖那一个内存对象还活着。
7

Tenant / Authorization 必须一路跟着 Run

Agent 能力越强，数据边界越不能交给模型自觉。
API boundary

调用者是谁？能创建/取消/审批哪个 run？

RunStore boundary

`run_id` 查询必须同时检查 `tenant_id`，不能只凭 UUID。

Tool boundary

目标资源授权在 ToolExecutor/adapter 层再次检查。

Memory boundary

USER / WORKSPACE scope 参与 retrieval，而不是检索完再让模型忽略。

Artifact boundary

handoff/ref 指向的数据也必须带访问控制。

Trace boundary

日志里避免泄漏 secret，审计身份和动作。

哪些组件必须从“课程内存版”换成生产基础设施？

接口可以保留，adapter 必须替换。
课程 baseline生产需要
InMemoryRunStore事务型持久数据库 / durable state store
InMemoryRunQueue真正 queue / broker / workflow scheduler
InMemoryCheckpointStore持久 checkpoint + revision/audit
MemoryStoretenant-scoped persistent store + retrieval/index
单进程 Workerworker pool / leases / concurrency / autoscaling
页面教学 tracestructured telemetry / metrics / traces / alerts
课程的价值是先把 contract 定清楚。以后接 Postgres、Redis、SQS、Celery、Temporal、LangGraph 等，不应该改变“run revision / checkpoint / approval / ownership / budget”这些核心语义。

Research Assistant v4.0：ProductionControlPlane

把 Agent 从单次函数调用提升成可管理的 Run。
control = ProductionControlPlane()

run = control.submit(
    run_id="run-42",
    tenant_id="team-a",
    objective="compare papers",
)

job = control.queue.pop()
claim = control.claim(job)

# side effect needs human
waiting = control.pause_for_approval(
    run.id,
    tenant_id="team-a",
    approval_request_id="approval:call-9",
    checkpoint_id="run-42:send-9",
)

# human resolved exact call
control.enqueue_resume_after_approval(
    run.id,
    tenant_id="team-a",
    approval_request_id="approval:call-9",
)
这个模块故意不执行模型本身。它是 control-plane teaching baseline：RunStore / Queue / revision / cancel / approval resume 的 contract。AgentLoop、DurableActionRunner、ApprovalManager、Handoff、Trace 都在 worker/runtime 侧组合。
