Agent 05 · Research Assistant v3.5

多个 Tool 不是“全部 gather 一下”。
真正要解决的是依赖、数据流、并行和 partial failure。

当 Agent 一次任务需要搜索多个来源、读取文档、合并结果、再继续下一步时，动作已经形成一个小型 DAG。工程上必须知道：哪些 action 现在 ready、哪些能并行、谁依赖谁、上游失败后下游该跳过还是带着 partial result 继续。

1

为什么顺序写一串 await 不够？

它能运行，但可能白白浪费延迟。
全部串行
a = await search_arxiv(q)
b = await search_crossref(q)
merged = await merge(a, b)

两个搜索互不依赖，却被迫排队。

依赖感知
search_arxiv  ─┐
               ├─→ merge
search_crossref┘

前两步可以并行，merge 必须等待二者。

并行化的依据是 dependency graph，不是“函数看起来都是 async”。

Action Graph 不只是控制顺序，还要传数据

上游 output 往往是下游 argument。
search_a.output→join.leftsearch_b.output→join.right
ActionNode(
    id="join",
    dependencies=["a", "b"],
    bindings={"left": "a", "right": "b"},
    tool_call=ToolCall(id="join-call", name="merge_results", arguments={}),
)
v3.5 会在真正执行 join 之前把 dependency output 注入参数，而不是让模型再手工复制一遍结果。

Fan-out / Fan-in 是最常见的模式

搜索、抓取、验证都经常这样。
Query
→
Source A
↘
Join
→
Rerank
Query
→
Source B
↗
fan-out 提高并发，fan-in 恢复一个统一状态。如果没有显式 join，后续模型往往要自己从多个异步结果里猜哪些已经齐了。
5

Partial failure：一条支路挂了，要不要全盘失败？

这取决于 dependency policy。
Policy含义适合
ALL_SUCCESS所有依赖都成功才执行必须拿齐输入的计算/写操作
ALL_DONE依赖只要都结束就可执行，失败输出可为空搜索聚合、best-effort、partial summary
Partial result 不是偷偷忽略错误。最终结果里应该显式保留 warning/缺口，后面 Eval 也要知道哪条支路缺失。
6

为什么不能无限 fan-out？

并发本身也是一种资源。
无限并发

1000 个 Tool 一次性发出去，可能把 API rate limit、浏览器、数据库连接池一起打爆。

Bounded concurrency

用 semaphore / worker pool 限制同时运行的 ready nodes。

ToolOrchestrator(
    executor,
    max_concurrency=4,
)
Agent 05 的 `max_concurrency` 是执行层边界；模型不应该自己决定“现在同时开 200 个浏览器”。
7

工具结果要统一成可 join 的 contract

否则每个 handler 都有自己的异常世界。
ActionResult(
    node_id="source_b",
    status="failed",
    output=None,
    error_type="timeout",
    error_message="source unavailable",
    wave=1,
)
后续节点只需要面对统一 `ActionResult`，而不是分别处理 requests exception、数据库 exception、浏览器 exception。
8

Orchestration 和 Planning 不是一回事

一个决定“做哪些事”，一个决定“这些事怎么安全执行”。
层负责
Plan任务有哪些 subgoal、依赖和 revision
Decision Maker此刻要采取什么 action
Orchestrator一组已确定 action 的 dependency / parallel / join / failure execution
ToolExecutor单个 Tool 的 validation / permission / handler execution
分层后以后换 LangGraph，只是 orchestration abstraction 变了，Tool contract 和 Plan contract 不用推倒重做。
