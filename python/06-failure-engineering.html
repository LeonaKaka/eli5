Python 06 · Research Agent v0.6

可靠系统不是“不失败”。
是知道失败后该怎么办。

当 v0.5 开始并发调用多个服务，失败会更常见：timeout、429、5xx、坏 JSON、权限错误、代码 bug。真正的工程能力不是把它们全 catch 掉，而是先分类，再选择正确策略。

1

先学最重要的一件事：不是所有错误都该 retry

点不同失败，看策略为什么完全不同。
记录
日志 / trace / metric
结果
恢复、降级或清楚失败
最危险的思想：“失败了就 retry 三次。”如果 API key 错、代码有 bug、请求本身非法，重试只是重复制造同一个失败。
2

Exception：把不同失败变成不同“信号”

异常不是为了把程序弄复杂，而是让调用者知道“发生了哪类问题”。
try:
    response = await client.get(url, timeout=5.0)
    response.raise_for_status()
    data = response.json()
except TimeoutError:
    ...
except RateLimitError:
    ...
except ValidationError:
    ...
好的异常处理

只 catch 你能真正处理的错误；处理不了就继续抛，让更高层决定。

坏的异常处理

except Exception: pass 把 bug、网络错、数据错全部抹平，最后只剩“怎么结果是 None？”

try:
    result = await search()
except Exception:
    pass   # ❌ 调试信息、失败原因、恢复机会全没了
3

Retry 为什么需要 Backoff，而不是连点刷新

上游已经过载，你立即重试可能正好让它更糟。
立即
attempt 1

点按钮看下一次尝试为什么越来越晚。

for attempt in range(max_attempts):
    try:
        return await call_api()
    except TemporaryError:
        if attempt == max_attempts - 1:
            raise
        delay = 2 ** attempt
        await asyncio.sleep(delay)
真实系统还常加 jitter。如果一万台客户端都严格等 1s、2s、4s，它们可能又同时醒来形成“重试风暴”；随机抖动可以把时间错开。
4

Logging：失败以后，你至少得能回答“发生了什么”

print 只告诉你一句话；结构化日志要能把一次请求串起来。

一条有用的日志通常包含

request_id / trace_id：把同一次用户请求的多个步骤串起来
tool / model / endpoint：到底哪个依赖失败
attempt / elapsed_ms：第几次、花了多久
decision：最后 retry、fallback 还是 fail fast
如果用户只说“刚才 Agent 卡住了”，你应该能靠 request_id 看到它卡在搜索、模型、数据库还是工具，而不是靠猜。

注意：return_exceptions=True 不是“错误自动解决了”。你只是把异常也收回来，后面仍要判断哪个源失败、是否允许部分结果、是否需要向用户披露。
6

Retry 有一个更危险的坑：副作用可能被执行两次

“查天气”重复两次没大事，“发邮件 / 扣款 / 创建订单”重复两次就完全不同。
🔎
通常较安全重试

只读搜索、GET 查询、无副作用计算。仍要考虑成本和限流。

📨
必须谨慎

发消息、创建资源、写数据库、支付、删除操作。第一次可能已经成功，只是响应丢了。

Agent Tool Calling 特别要注意：工具超时不代表“工具没有执行”。对有副作用操作，应考虑 idempotency key、操作状态查询、human approval 或显式去重。
7

什么时候 Fail Fast，什么时候继续？

可靠不是“永远尽量返回东西”，有些条件下继续执行反而危险。
情况常见策略原因
搜索源 timeoutretry / partial暂时性，且其他来源可用
429wait / limit需要尊重限流而不是立即重试
认证失败fail fast同一凭据重复尝试没有意义
响应缺字段validate / fallback不能把坏数据当正常数据继续传
删除操作状态不明stop / verify盲目重试可能重复副作用

Research Agent v0.6：从“会联网”升级到“可恢复地联网”

现在搜索层不仅并发，还明确区分 transient failure、bad data 和 fatal configuration。
async def safe_search(query: str):
    try:
        return await call_with_retry(
            lambda: search_web(query),
            max_attempts=3,
        )
    except TemporaryError as exc:
        logger.warning("web search unavailable", extra={"error": str(exc)})
        return []

async def gather_evidence(query: str):
    arxiv, web = await asyncio.gather(
        search_arxiv(query),
        safe_search(query),
    )
    return {"arxiv": arxiv, "web": web}
练习 A · 选策略

LLM 返回 401，你应该：A. 立即 retry 10 次；B. fail fast 并检查配置；C. 无限 backoff。

答案

B。认证失败通常不是暂时性网络问题，重复同一凭据没有意义。

练习 B · Agent 副作用

“发送邮件”工具调用 5 秒后 timeout。你能不能直接再调用一次？

答案

不能默认安全。第一次可能已经发出，只是确认响应丢失。应查询状态、使用幂等机制或让工具设计支持去重。
