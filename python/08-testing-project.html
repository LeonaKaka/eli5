Unit / Integration / E2E：别把所有测试都做成一种

越往上越接近真实系统，也越慢、越脆、定位越困难。
少量 E2E · 整条路径真的能走通
Integration · 几个真实组件一起工作
大量 Unit · 小函数/小对象行为
层级例子失败时告诉你什么
UnitAgentState 默认 list 是否隔离一个很小的行为坏了
Unitretry 只对 TransientError 生效错误策略坏了
IntegrationResearchAgent + 两个 fake sources组件组合有问题
E2ECLI → validation → agent → output最终用户路径坏了
常见误区：“E2E 最真实，所以全部写 E2E。”结果是测试慢、失败难定位、外部 API 抖一下整套 CI 全红。

pytest 最小核心：Arrange → Act → Assert

先准备场景，再执行行为，最后检查结果。
def test_state_has_isolated_messages():
    # Arrange
    a = AgentState()
    b = AgentState()

    # Act
    a.messages.append({"role": "user", "content": "hi"})

    # Assert
    assert len(a.messages) == 1
    assert b.messages == []
这个测试同时验证了上一课的 default_factory=list：如果两个实例错误共享 list，第二个 assert 会直接抓出来。

真实 timeout 很难“每次测试时刚好发生”。Mock 能精确注入第一次失败、第二次成功，从而验证 retry。
5

什么不该 mock？

Mock 太多会让测试只证明“你自己设定的假世界能工作”。
适合 mock/fake

远程 API、时间、随机数、邮件、支付、昂贵模型调用、很难稳定制造的失败。

尽量真实

自己的纯函数、数据模型、排序逻辑、状态更新、简单序列化；integration test 里让自己的组件真组合。

判断标准：测试目标是什么？如果你正在验证“Agent 收到两个 source result 后怎么组合”，那 source 可以 fake；如果你正在验证“HTTP client 能不能正确解析供应商 JSON”，HTTP client 自己就不能被 mock 掉。

怎么运行它

这个 v1.0 默认使用本地 Demo sources，不需要 API key，先保证你能完整跑通工程结构。
cd projects/research-agent-lite
python -m venv .venv
source .venv/bin/activate   # Windows 用 .venv\Scripts\activate
pip install -e ".[dev]"

python -m app.main "RAG evaluation"
pytest -q
为什么先不用真实模型？因为这一阶段验收的是 Python 工程骨架。下一阶段“LLM 应用开发”再把真实模型 client 接进来，会更容易判断问题到底来自 Python 工程还是模型本身。
