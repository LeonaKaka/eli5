Embedding 很会找“意思相近”。
但有些查询要找的是“这个字符串就是它”。

论文 DOI、错误码、型号、缩写、基因名、函数名、法律条款号，都可能让纯 dense retrieval 吃亏。BM25 代表的是另一种能力：按词项匹配，并给稀有且有区分度的词更高权重。真正稳健的检索常常不是二选一，而是 dense + lexical 的 Hybrid Search。

4

为什么不能直接 `0.5 * cosine + 0.5 * BM25`？

两个 score 通常不在同一个刻度。
Dense score

可能是 cosine，常落在一个很窄的数值区间；不同 embedding/model/distribution 下范围也不同。

BM25 score

没有天然和 cosine 对齐的绝对尺度，查询长度和词项分布也会改变数值。

坏做法：看到两个都是 float 就直接相加。这样权重常常只是“谁的数值范围更大谁赢”。
5

RRF：不管原始分数，先看各自排第几

Reciprocal Rank Fusion 是很实用的 rank-level fusion 思路。
RRF(doc) = Σ 1 / (k + rank_i(doc))
Dense rank
↘
RRF
→
Hybrid rank
←
BM25 rank

同一文档如果在 dense 和 BM25 都排得靠前，会得到更高融合分；只在其中一路很强，也仍然有机会进入候选集。

RRF 的好处之一是不用假设两个原始 score 已经校准到同一尺度。代价是它主要利用排名，不利用分数差距本身。
6

Lexical retrieval 也有自己的工程坑

“关键词搜索”不是一个 `.split()` 就结束。
问题为什么重要
Tokenization中文、英文、代码、DOI、连字符、下划线的切法不同
大小写 / normalizationAPI 名、基因名、产品型号有时不能随便归一化
Stop words常见词可降低区分度，但领域术语不能误删
Stemming / lemmatization能合并词形，也可能损伤精确术语
Field weightingtitle、heading、body、caption 的命中价值可能不同
科研检索尤其要小心 identifier。DOI、材料名、样品编号、公式符号如果 tokenizer 切坏，BM25 的精确匹配优势也会被你自己破坏。
7

Hybrid Search 不是“永远比单路好”

它增加召回机会，也增加系统复杂度。
收益

同义表达由 dense 补，精确 token 由 lexical 补。

代价

两套索引、两路查询、融合策略、更多 latency 和观测。

验收

必须在真实 query slice 上比较 Dense-only / BM25-only / Hybrid。

如果你的 query 95% 都是固定 SKU/错误码，BM25 可能已经很好；如果都是自然语言知识问答，dense 可能占主导。Hybrid 应该由 eval 证明，而不是因为“架构更高级”。
8

Research Assistant v2.5：Lexical + Fusion boundary

Chunk id 继续作为共同主键，不再发明另一套文档表示。
lexical.upsert(chunks)

bm25_hits = lexical.search(query, k=50)
dense_hits = dense.search(query_vector, k=50)

hybrid = reciprocal_rank_fusion(
    [dense_hits, bm25_hits],
    rrf_k=60,
)
项目原则：不同 retriever 返回统一可追踪的 hit id；fusion 只融合 ranking，不丢掉来源、retriever 名称和原始 rank，方便后面做 error analysis。
