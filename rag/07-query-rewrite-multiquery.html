RAG 07 · Research Assistant v2.7

有些问题不是“搜不到”。
是你拿错 Query 去搜了。

用户的问题是为人类交流写的，不一定天然适合 retrieval。它可能含指代、比较、多跳关系、上下文省略或一次塞了三个子任务。Query Planning 的工作是：保留用户原意，把问题变成更容易检索、可分别验证的搜索任务。

1

Retriever 看到的 Query，未必应该等于用户原话

但改写也不是越多越好。
User question
→
Query Planner
→
Search Query[]
→
Retrieve / Merge
→
Evidence
两个目标同时存在：提高 retrieval recall，同时不能让 rewrite 改变用户真正问的问题。
2

Interactive：四种 Query Strategy 到底差在哪？

同一个复杂科研问题，切换 original / rewrite / multi-query / decomposition。
观察重点：Multi-query 主要增加“表达覆盖”；decomposition 则是在处理真正多个子问题，二者不是同义词。
3

Rewrite：把表达变好，不是偷偷替用户改问题

Rewrite drift 是很常见的隐形 bug。
允许的变化

补全代词、展开缩写、把口语改成检索友好术语、带入明确的对话上下文。

危险变化

新增用户没说的时间、材料、机制、结论；把“比较”改成“证明 A 更好”。

工程上最好保存：original_query、rewritten_query、planner_version。这样 retrieval 变差时你能看见到底搜了什么。
4

Multi-query：用多种表达增加召回机会

特别适合同义表达丰富、文档术语不统一的场景。
queries = [
  "random-field disorder coercive field",
  "quenched disorder switching threshold",
  "disorder dependence of Ec",
]

hits = [retrieve(q, k=20) for q in queries]
merged = dedup_and_fuse(hits)
收益

不同 query 可以命中不同术语表述。

代价

检索请求增多、结果重复、延迟和成本增加。

风险

差的 query expansion 会把候选集合带偏。

不是 query 越多 recall 就无限涨。每条 query 都应该有明确意图，最终也必须 merge / dedup / trace。
5

Decomposition：有些问题本来就不是一次检索能回答

比较、多跳、条件推理最典型。
比较 A/B 方法差异
→
找 A 方法
+
找 B 方法
+
找 Ec 机制证据
→
综合比较
这里最后一步不是 retrieval。它是基于多个已验证 evidence 的 synthesis。把整个问题硬塞成一个 embedding query，常常会丢掉部分约束。
6

Conversation-aware Rewrite：把“它”“那个实验”补完整

但不要把整段聊天史永久复制进 query。
history:
user: 比较论文 A 和 B
assistant: ...
user: 那它的器件尺寸呢？

resolved query:
"论文 B 的器件尺寸是多少？"
先做 referent resolution，再检索。如果直接搜“它的器件尺寸”，embedding 可能完全不知道“它”指谁。
7

Query Routing：不是所有 Query 都应该走同一套 Retriever

前面学过的 BM25 / dense / metadata filter 开始组合起来。
Query 类型更合理路线
DOI / 错误码 / SKULexical-first + exact field
自然语言概念问题Dense + BM25 hybrid
“2025 年以后”metadata pre-filter + retrieval
多论文比较decompose → per-source retrieve → merge/rerank
这其实已经在形成一个小型 Retrieval Planner：先理解 query 类型，再决定怎么查，而不是所有请求都 `vector.search(k=10)`。
8

怎么 Eval Query Rewrite？

不能只评价“rewrite 看起来更专业”。
指标检查什么
Intent preservation改写后是否仍然是原问题
Recall@Krewrite/multi-query 是否真的多召回相关证据
Drift rate是否引入原问题不存在的实体/条件
Query count / latency多 query 的收益是否值得额外成本
Slice指代、比较、identifier、多跳分别表现如何
真正的验收问题：不是“LLM 改写得顺不顺”，而是“改写后相关证据更容易被找到，而且没有改题”。
9

Research Assistant v2.7：QueryPlan 成为显式对象

不要让 rewrite 字符串在业务代码里悄悄覆盖原 query。
plan = planner.plan(
    "比较论文 A 和 B 的方法差异，并解释为什么 A 的 Ec 更低"
)

# plan.original_query
# plan.search_queries
# plan.strategy
# plan.version
# plan.requires_synthesis
后面的 retrieval trace 可以明确记录：哪条 search query 命中了哪条 chunk，最终证据是从哪一路 query 进来的。
