RAG
RAG 06 · Research Assistant v2.6

Retriever 负责“别漏”。
Reranker 负责“别把次相关的放前面”。

第一阶段为了快，通常只能用相对便宜的 dense / BM25 信号，从海量文档里捞几十个候选。Reranker 可以花更多计算，把Query 和每个候选放在一起重新判断相关性，再只把真正最值得看的少数证据交给 LLM。

1

为什么已经有 cosine/BM25 还要再排一次？

第一阶段搜索的约束和最终精排的约束不同。
First-stage Retriever

要在 10 万、100 万、上亿候选中快速搜索。

目标：高 recall，便宜、可索引。

Reranker

只看已经筛出的几十个候选，可以使用更贵的 query-document 联合判断。

目标：高 precision，把前几名排对。

本质：不是“第一次检索失败了再补救”，而是两阶段系统故意把召回和精排拆给不同模型。
2

Bi-encoder 与 Cross-encoder 的直觉

为什么 dense embedding 能建索引，而 cross-encoder 往往不能直接扫全库。
Bi-encoder / Embedding
embed(query)   → q
embed(chunk)   → d
score(q, d)

文档向量可以提前算好，所以查询很快。

Cross-encoder / Reranker
model([query, chunk])
        ↓
 relevance score

每个 query-chunk pair 都要重新计算，但能更细地看词间交互。

Reranker 更贵的原因也正来自这里：它不是查一个预计算向量，而是对每个候选重新看一次 query + document。

Latency 组成（教学示意）：

最重要的一句话：Reranker 只能重排“已经召回”的候选。真正相关文档如果在 first-stage 排第 60，而你只拿 top-20，后面再强的 reranker 也看不到它。
4

所以 Candidate K 是 Recall 和成本的旋钮

越大不一定越好，但太小会把 recall ceiling 锁死。
Candidate K收益代价
太小便宜、快相关文档可能根本进不了 reranker
适中覆盖更多弱排序候选增加 rerank latency
太大更高候选 recall计算、成本、尾延迟上涨；很多候选明显无关
正确做法是画 candidate recall vs rerank latency，而不是拍脑袋固定 `retrieve_k=100`。
5

Rerank score 解决的是“这个 Query 下谁更相关”

不要把它误当成全局文档质量分。
Query A

“无序如何影响 Ec？”

Chunk X relevance = 0.96

Query B

“实验器件用了什么电极？”

同一个 Chunk X relevance = 0.12

因此：reranker score 通常是 query-conditioned。跨不同 query 比较 `0.82 > 0.73` 常常没有你想象的全局意义。
6

Cross-encoder、LLM Reranker、规则各放在哪？

不是所有重排都必须用最大 LLM。
方式适合代价/风险
Cross-encoder大量 query-document relevance 精排需模型推理，但通常比生成式 LLM 更可控
LLM Reranker复杂 rubric、多条件判断、少量高价值候选更慢、更贵、输出和 prompt 也需 eval
Deterministic rules时间过滤、权限、精确字段、硬约束表达力有限，但稳定可解释
工程习惯：硬规则能做的，不要全交给 reranker 学；权限过滤甚至应该更早在 retrieval candidate 阶段就完成。
7

Reranking 之后还要处理近重复和 Evidence Diversity

最高相关的 5 个 chunk 可能其实是同一段的 5 个 overlap 副本。

→

→

→
Evidence top-5
只看 relevance

五条结果全来自同一个 paragraph，信息高度重复。

加 diversity

保留核心证据，同时允许方法、结果、图表等互补来源进入 context。

这也是为什么 RAG eval 不能只测“是否命中一篇文档”，后面还要看 citation、证据覆盖和 context packing。
8

怎么单独 Eval Reranker？

先不要让生成模型把问题混进来。
检查回答的问题
MRR / nDCG相关结果有没有被推到更靠前？
Top-N precision给 LLM 的少数证据里有多少真相关？
Candidate recallfirst stage 有没有先把答案捞进来？
Latency p95rerank 候选增大后尾延迟是否可接受？
Slice中文、长 query、identifier、表格 query 是否表现不同？
诊断顺序：如果 candidate recall 已经很差，先修 retrieval；如果 candidate recall 高但最终 top-5 很差，再重点看 reranker。

reranked = reranker.rerank(
    query=query,
    candidates=candidates,
    top_n=5,
)

# 真实 adapter 以后可替换成 cross-encoder / API reranker
边界要保留：first-stage rank/score、rerank score、reranker version。否则最终第 1 名变了，你不知道是 retrieval 还是 rerank 导致的。
