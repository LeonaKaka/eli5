RAG 01 · Research Assistant v2.1

RAG 的第一步不是 Embedding。
是先别把文档读坏。

很多 RAG 系统从一开始就把 PDF 当成一长串字符串。问题是论文里有双栏、标题层级、图注、表格、公式、脚注、页码和扫描页。如果这些关系在解析时丢了，后面再强的向量库也找不回原来的结构。

1

Asset ≠ Document ≠ Chunk

先把三个层次分开，后面才不会把“文件处理”和“检索单元”混在一起。
Asset
原始 PDF/HTML
→
Document
结构化内容
→
Chunk
检索单元
层负责什么例子
Asset文件身份、权限、生命周期paper_42.pdf
Document章节、段落、表格、图、来源位置Section 3 / Fig.2 / page 7
Chunk为了 retrieval 而切出的可检索片段Methods 段落 + 标题上下文
核心：RAG ingestion 最好先产出稳定的 Document Model，再由不同 chunker / indexer 消费，而不是解析器直接吐“一堆字符串”。
2

切换解析模式，观察哪些关系会被破坏。

3

Document Model 应保留什么？

不是越复杂越好，而是要保留后面 retrieval / citation 真会用到的结构。
Document(
    id="doc_42",
    asset_id="paper_42",
    title="Disorder-driven switching...",
    blocks=[
        Heading(level=2, text="Methods", source=page2),
        Paragraph(text="...", source=page2),
        Figure(caption="...", source=page3),
        Table(cells=[...], source=page4),
    ],
)
内容

text、caption、cells、formula text。

结构

heading level、block type、reading order。

来源

page、region、asset id、parser metadata。

4

为什么 reading order 会直接影响检索？

双栏论文最典型。
❌ 错误顺序

左栏第 1 段 → 右栏第 1 段 → 左栏第 2 段 → 右栏第 2 段。

后面 chunker 会把本来不相邻的句子拼在一起。

✅ 正确顺序

先完整读左栏，再进入右栏；标题、图注作为单独 block 保留。

Chunk 才能继承正确语义边界。

解析错误往往不是“回答立即乱码”，而是更隐蔽：Embedding 仍然能算，检索也能返回结果，只是结果的语义已经被污染。
5

表格不能只 `\n`.join()

表格的意义来自行列关系。
压平后
L 64 128 256
Ec 0.42 0.39 0.38

简单问题还勉强能用，但复杂表格很快丢失“哪个值属于哪个列”。

结构化后
{
  "columns": ["L", "Ec"],
  "rows": [[64,.42],[128,.39],[256,.38]],
  "source": {"page":4,"table":1}
}

后面既能生成文本表示，也能直接做结构化查询。

不要假设所有内容都必须最终变成纯文本。RAG 的 evidence 可以是文本、结构化表格、图像 crop 或它们的组合。
6

OCR：只在需要时使用，而且要带 confidence

扫描件需要 OCR，但 OCR 不是“真值生成器”。
Page image
→
OCR
→
text spans
→
confidence
→
Document blocks
TextSpan(
    text="coercive fie1d",
    confidence=0.71,
    source=SourceRef(asset_id="paper_42", page=3, region=(...)),
)
好处：后面如果回答依赖低置信度 OCR 片段，可以触发“重新看原图 / 人工确认”，而不是把识别错误伪装成确定事实。
7

Parser 也要可替换、可评估

不同文档类型可能需要不同 parser。
class DocumentParser(Protocol):
    def parse(self, asset: AssetRef) -> Document: ...

class NativePdfParser: ...
class ScannedPdfParser: ...
class HtmlParser: ...
不要在业务层写：if file.endswith('.pdf'): ... 然后散落几十个解析分支。把 parser 能力放在 ingestion 边界，才能独立测试和替换。
8

怎么评估 Parser？

不是“肉眼看起来差不多”。
检查示例
Reading order双栏顺序是否正确
Structure recall标题、图、表是否被识别
Text fidelity字符/公式/OCR 是否错误
Provenance每个 block 是否还能回到 page/region
Downstream impact换 parser 后 retrieval recall 是否提高
最后一项很重要：Parser 不只是“文档工程”的指标，它最终要看是否让检索和回答更可靠。
