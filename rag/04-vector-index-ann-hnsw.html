Vector DB 的核心不是“存向量”。
是大规模下怎样快速找到足够近的邻居。

1 万个 chunk 时，遍历全部向量可能还能接受；1 亿个时就不现实。ANN 用“允许极小概率漏掉真正最近邻”换取巨大速度收益。HNSW 是最常见的图索引思路之一：先在稀疏高层快速靠近目标，再下到密集底层精搜。

HNSW 里最常见的三个旋钮

名字可能因实现略有差异，但 trade-off 相似。
参数大致影响代价
M每个节点保留更多图连接索引更大、构建更重，通常 recall 更好
efConstruction建图时探索更多候选构建慢，但图质量通常更好
efSearch查询时探索更多候选延迟升高，Recall@K 通常提高
没有万能参数。应该在自己的数据规模和真实 query 上画 recall-latency curve，而不是抄博客里的 M=16 / ef=64。

Interactive：同一个 Query，Exact 和 ANN 结果可能不同

把 efSearch 拉低，再点 ANN。
如果低 efSearch 漏掉 #2 真邻居，这不是“数据库坏了”，而是 approximation trade-off。你要决定这个损失是否被业务允许。
7

Vector DB 还负责哪些东西？

生产系统远不止 ANN 算法。
Storage / Upsert

向量、chunk id、metadata、删除、增量更新。

Filtering

按 tenant、paper、year、权限等 metadata 过滤。

Operations

持久化、分片、复制、备份、监控、容量。

所以 FAISS、pgvector、Qdrant、Milvus、Pinecone 不是“谁支持向量谁就完全等价”。它们在部署、过滤、事务、运维和规模上定位不同。
8

Metadata filter 放在哪一步，会影响性能和 recall

Pre-filter 和 post-filter 不是一回事。
Pre-filter

先限制“只能搜这 1000 个候选”，再做向量搜索。

权限/租户隔离通常更自然。

Post-filter

先 ANN 找 top-k，再把不符合 metadata 的扔掉。

可能最后只剩很少结果。

权限过滤尤其不能靠模型。未授权 chunk 最好根本不要进入候选集合，而不是检索出来后再叫 LLM “不要引用”。
