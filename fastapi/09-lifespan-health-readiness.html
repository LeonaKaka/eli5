服务“进程还活着”，
不代表它现在应该继续接用户流量。

真正的 Agent API 会长期持有 DB pool、HTTP client、queue connection、checkpoint/event backend。它们必须有明确 owner、startup、shutdown；同时把 liveness 和 readiness 分开，否则一次数据库抖动就可能触发整组容器重启风暴。

2

FastAPI lifespan 是资源 ownership contract

resources = RuntimeResourceManager(...)

app = FastAPI(
    lifespan=resources.lifespan,
)

@asynccontextmanager
async def lifespan(app):
    await resources.start()
    try:
        yield               # 服务开始接请求
    finally:
        await resources.close()
重点不在 `asynccontextmanager` 语法，而在 只有一个地方拥有资源生命周期。Endpoint 只“借用”依赖，不负责偷偷创建/销毁全局连接。
3

Liveness 和 Readiness 为什么必须分开？

/health/live“这个进程 / event loop 还能回答吗？”——不要因为 DB 暂时挂了就自杀重启。200
/health/ready“如果现在给我新流量，我能正确服务吗？”——required dependency 挂了就摘流量。503
错误做法：liveness 每次都 ping DB。DB 集群抖 20 秒 → 所有 API pod liveness 失败 → 编排器同时重启所有 pod → 故障被放大。

Optional dependency 不一定应该把整个 API 摘掉
比如核心研究请求只依赖 RunStore + Queue + Graph checkpoint，而一个 analytics sink 只是辅助遥测。analytics 掉了：
live  = 200
ready = 200
analytics = degraded
反过来，如果 Queue 是创建 Run 的必要路径：
live  = 200
ready = 503
job_queue = not ready
Readiness 本质是一个产品可服务性策略，不是“所有依赖都必须 100% 正常”的机械 AND。
6
Startup 中途失败，也要清理已经打开的资源
await db.start()       ✅
await queue.start()    ✅
await event.start()    💥

不能直接退出：
DB / Queue 连接已经打开

正确：
close(queue)
close(db)
raise startup error
v5.9 的 `RuntimeResourceManager.start()` 已经把 partial-start cleanup 写成回归边界；这类 bug 本地跑一次不明显，但滚动发布/反复重启时很容易积累。
7
Health endpoint 不需要用户 Bearer token
GET /health/live
GET /health/ready

→ 不挂 RunReadPrincipal
→ 给 LB / orchestrator 使用
→ 只返回最小 operational state
→ 不暴露 secrets / DSN / exception traceback
它们的受众不是最终用户，但也不代表可以把数据库连接串、内部 host、checkpoint 内容塞进去。
