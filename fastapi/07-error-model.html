07 · Research Assistant v5.7

状态码告诉客户端“哪一类失败”。
稳定错误 body 告诉它“接下来该怎么办”。

前面我们已经有 401 / 403 / 404 / 409 / 412 / 422 / 428，但 body 仍来自不同地方的 `HTTPException(detail=...)`。v5.7 把它们统一成一个 ProblemDetails 外壳，同时保留不同状态语义，并为每次失败生成 server-side `request_id`。

为什么要接管 RequestValidationError？
FastAPI 会把请求校验失败包装成 `RequestValidationError`。v5.7 只投影 `location / message / type`，不把原始 request body、内部 Python 异常或调试上下文直接回给客户端。
errors = [
  {
    "location": "body.objective",
    "message": "Value error, ...",
    "type": "value_error"
  }
]
日志 ≠ response。调试时你可以在私有 telemetry 里关联更多信息；公开 API 不需要知道源码文件名、堆栈或整份原始 body。


5
为什么还要接管 Starlette HTTPException？
@app.exception_handler(StarletteHTTPException)
async def http_exception_handler(request, exc):
    return problem_response(
      status=exc.status_code,
      detail=public_detail,
      headers=exc.headers,
    )
这样认证 dependency 抛出的 401、permission 403、Run lookup 404、command 409/412/428 都能得到相同 public shape。同时要保留 `WWW-Authenticate: Bearer` 这类有协议意义的 header。


6
500 必须比 4xx 更保守
❌ 不要
{"detail":"KeyError at /srv/app/... checkpoint=cp-secret ..."}
✅ 公共响应
{
  "code":"internal_error",
  "detail":"An unexpected server error occurred.",
  "request_id":"req-..."
}
真实 exception 进入私有日志/trace，并用 `request_id` 关联。客户端只需要知道这是服务端故障和它的 correlation id。

Request ID 是错误协议和 observability 的桥
HTTP request
→
server generates req-123
→
Problem body + header
→
private logs / trace
request_id 不是用户身份、tenant id 或安全 token。它只是 correlation handle，方便支持/工程人员定位同一次请求。


8
OpenAPI 也应该知道失败长什么样
@app.post(
  "/runs/{run_id}/cancel",
  response_model=RunResponse,
  responses=problem_responses(
    400, 401, 403, 404,
    409, 412, 422, 428, 500,
  ),
)
Exception handler 解决“运行时返回什么”，`responses=` 解决“客户端生成器和 `/docs` 知道什么”。两边缺一边，contract 都不完整。
