Backend Track
01 · Research Assistant v5.1

第一个 FastAPI endpoint 不该是 Hello World。
它应该先把“产品资源边界”做对。

我们已经有 RunStore、Queue、Worker 和 LangGraph。现在 FastAPI 的职责是把这些能力变成 HTTP resource：客户端提交一次研究任务，服务器返回一个 Run；长任务继续由后台 Worker 执行，而不是把 Agent 塞进 HTTP request 里等十分钟。

1

先看错误架构

“endpoint 里 await agent.run()”在 demo 很爽，生产会把请求生命周期和长任务生命周期绑死。
❌ Inline Agent
@app.post("/research")
async def research(req):
    return await agent.run(req)

客户端断连、超时、Worker 重启、审批暂停都会和 HTTP request 粘死。

✅ Run Resource
POST /runs
→ create Run
→ enqueue job
→ 201 Created

真正执行发生在 Queue/Worker；HTTP 层只负责资源 contract。

2

ASGI 在这里是什么角色？

FastAPI 基于 Starlette/Pydantic，运行在 ASGI server 上。
ClientHTTP request / response
ASGI Server例如 Uvicorn，接 socket 并驱动 ASGI app
FastAPI / Starletterouting、dependencies、middleware、response
Pydanticrequest/response data contract
Our ApplicationRunStore / Queue / LangGraph runtime
边界重点：FastAPI 能 async 处理 request，不代表它自动变成 durable job queue。

4
为什么 POST 返回 201，而不是 200？
HTTP status 本身就是 contract。
POST /runs → 201 Created
服务器创建了新的 Run resource。
GET /runs/{id} → 200 OK
资源存在并成功读取。
GET unknown → 404
当前 tenant 看不到这个 resource。
Invalid request → 422
body/header contract 不满足。
FastAPI 的 `status_code=` 还会进入 OpenAPI 文档，不只是运行时改一个数字。
5
Path operation 是 HTTP adapter，不是业务核心
@app.post(
    "/runs",
    response_model=RunResponse,
    status_code=201,
)
async def create_run(body, tenant, runtime):
    run = runtime.submit(
        run_id=...,
        tenant_id=tenant.tenant_id,
        objective=body.objective,
        approval_required=body.approval_required,
    )
    return RunResponse.from_record(run)
这里没有直接调 `graph.invoke()`。这正是 v5.0 架构在 HTTP 层的延续。
6
OpenAPI 为什么不是“自动 Swagger 漂亮页面”这么简单？
POST/runs201GET/runs/{run_id}200
FastAPI 会把 path、request schema、response schema、header dependency 和 status codes 汇总成 OpenAPI。后面 08 会把它当 regression contract，而不是只当手工试接口的页面。
