POST 只负责提交 Run。
那“运行中发生了什么”就应该走独立 stream。

对于 Agent 这种主要是服务端向客户端推状态的长任务，SSE 很合适：HTTP 语义简单、浏览器原生支持 EventSource、天然有 `id / event / data`，还能通过 Last-Event-ID 做断线续传。真正难的不是“会 yield”，而是事件 schema、重连、retention、disconnect、backpressure 和安全投影。

1

为什么这里先选 SSE，而不是一上来 WebSocket？

需求是单向“服务器持续推 Run 进度”，不是双向实时控制协议。
SSEWebSocket
方向Server → Client双向
协议普通 HTTP 长连接升级为 WebSocket
事件 id / reconnect协议天然支持通常自己设计
适合本项目progress / status / approval notification以后若需要高频双向协作再考虑
不是说 WebSocket 不好，而是别为了“实时”就自动选更复杂的协议。
2

FastAPI 现在有原生 SSE response

官方主路径就是 path operation 直接 `yield`，让 SSE 路由层处理序列化和保活。
from collections.abc import AsyncIterator
from fastapi.sse import (
    EventSourceResponse,
    ServerSentEvent,
)

@app.get(
    "/runs/{run_id}/stream",
    response_class=EventSourceResponse,
)
async def stream_run(...) -> AsyncIterator[ServerSentEvent]:
    yield ServerSentEvent(
        id="17",
        event="progress",
        data={
          "phase": "retrieve",
          "progress": 35,
        },
    )
FastAPI 的 SSE 路由层会处理常见基础细节：空闲连接 keep-alive ping、`Cache-Control: no-cache`、以及避免某些代理缓冲。我们的 400/404/409 preflight 校验则放在 dependency 里，所以会在 stream 真正开始前返回普通 HTTP error。

一条 SSE 事件在线上长什么样？

id: 18
event: progress
data: {"run_id":"run-42","phase":"rerank","progress":60}

id: 19
event: completed
data: {"run_id":"run-42","status":"completed","progress":100}

这里 `id` 不是数据库主键，而是客户端重连 cursor；`event` 是客户端可路由的稳定类型；`data` 是公开 payload。

6

重连不是“重新开连接”这么简单

你必须回答：客户端错过的事件从哪里补？
Last-Event-ID: 17

server:
list_after(after_sequence=17)
→ #18
→ #19
→ #20

所以 SSE 需要某种 event log / cursor storage。当前课程版 `InMemoryRunEventStore` 是有界内存日志，只为验证协议；多 Worker / 重启环境必须换 durable broker、数据库日志或流系统。

如果客户端断得太久，历史已经被 retention 清掉呢？

最糟糕的是静默从“当前剩余事件”继续，让客户端误以为历史完整。
client cursor = 1
→
server oldest = 4
→
history gap
→
409 + refetch state
不要伪造完整性。如果事件日志已经无法满足 resume cursor，就明确告诉客户端先重新 GET `/runs/{id}` 建立新的事实基线。
8

Disconnect / heartbeat / backpressure 分别是谁的问题？

问题本课处理生产还要考虑
空闲连接被 proxy 关闭SSE ping / no-cache / no bufferingLB idle timeout 配置
客户端主动断开`request.is_disconnected()` / cancellation不要继续做只为这个连接服务的 work
客户端读得慢yield/send 会产生流控bounded buffer、慢消费者策略
服务重启课程内存日志会丢durable event log + Last-Event-ID

Worker 可以发事件，但 SSE endpoint 不应该成为 Worker

stream 只是读取进度，不负责执行 Agent。
Worker
→
Event Store / Broker
→
GET /stream
→
Browser
# worker
outcome = await run_one_worker_tick(...)
events.append(event="completed", ...)

# API stream
for item in events.list_after(cursor):
    yield ServerSentEvent(...)
这条数据流很重要：用户断开 SSE 不应该导致 Worker 丢 ownership，也不应该自动 cancel Run。
