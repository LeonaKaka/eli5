05 · Research Assistant v5.5

“用户点了批准”不是一句业务描述。
它是一个可能重试、重复、过期的 HTTP command。

移动网络会重试、浏览器会双击、代理会重发、两个标签页可能同时操作同一个 Run。对于 approval / cancel 这种改变控制面的请求，只写一个 `POST` endpoint 远远不够：你还需要 revision precondition + idempotency key + exact target identity。

重复推进风险
“POST 不是幂等”不是借口。某个 HTTP method 的通用语义，不等于你的业务 command 可以接受重复副作用。
2

三把锁分别解决不同问题

Exact target`/approvals/{approval_request_id}`：批准的是这一份具体 pending approval。
If-Match / ETag“我是在 revision=3 的事实基础上发 command。” 防 stale client。
Idempotency-Key“这是同一次逻辑 command 的网络重试。” 防重复执行。
它们不能互相替代。ETag 不知道两个请求是不是同一个 command；Idempotency-Key 也不知道客户端依据的 Run state 是否已经过期。

你应该观察到

同 key + 同 command：第二次返回同一 response，并标记 replay。

同 key + 改 decision：409，因为 key 已经绑定到另一条逻辑 command。

新 key + stale If-Match：412，因为你在旧事实基础上修改资源。

没有 If-Match：428，服务器要求客户端先声明 precondition。

4

为什么先检查 Idempotency，再检查当前 revision？

因为一次成功 command 本来就会把 revision 改掉。
第一次：
If-Match: "3"
Idempotency-Key: approve-001
→ execute
→ Run revision = 4
→ save response for approve-001

网络超时，客户端重试：
If-Match: "3"
Idempotency-Key: approve-001

如果你先看 current revision：
3 != 4 → 412 ❌

正确：
先命中 approve-001 的已完成记录
→ replay 原 response ✅

所以 idempotency registry 不只是“记一个 key 用过没”，而是要把 key 与 command fingerprint 和原始结果绑定起来。

5

并发请求还有一个更隐蔽的竞态

Request A: lookup(key) → missing
Request B: lookup(key) → missing
Request A: approve() → enqueue RESUME
Request B: approve() → enqueue RESUME
Request A: remember(key)
Request B: remember(key)
这仍然不是幂等。课程版 `InMemoryIdempotencyStore.execute_once()` 把 lookup → execute → remember 放进同一个临界区。生产系统则需要数据库 unique constraint / atomic reservation / Redis 原子操作等跨副本方案。
6

真实 API：Approve / Reject

POST /runs/{run_id}/approvals/{approval_request_id}
Authorization: Bearer ...
If-Match: "3"
Idempotency-Key: approve-001
Content-Type: application/json

{
  "decision": "approve"
}

成功时应用层先校验 tenant、permission、approval_request_id 和 revision，再调用 v5.0 的 `resolve_approval()`；只有通过之后才 enqueue RESUME。重复网络请求不会再次 enqueue。

7

Cancel 也不是“一律立刻 CANCELLED”

QUEUED / WAITING_APPROVAL

还没有 active side effect ownership，可以直接进入 CANCELLED。

RUNNING

只能先 CANCELLING；Worker 在安全边界 acknowledge 后才是 CANCELLED。

POST /runs/{run_id}/cancel
Authorization: Bearer ...
If-Match: "7"
Idempotency-Key: cancel-004
HTTP cancel 不会穿越时间。如果外部 Tool 已经产生副作用，Run 停止也不能自动撤销现实世界；仍要回到 durable execution 的 reconcile / compensation。
8

HTTP status 在这里表达什么？

状态含义客户端下一步
200command 成功，或同 key replay 原结果使用 response / ETag
409业务状态冲突，或同 key 换了 command不要盲重试；重新理解状态
412If-Match 与当前 revision 不一致GET 最新 Run，再决定
428缺少必要 precondition先 GET ETag，再提交 command
401/403认证/授权失败进入下一课
