`async def` 解决的是等待方式。
它不是“把长任务自动搬到后台”。

你已经有一个可能跑几分钟甚至几小时的 Agent。现在最大的坑不是“FastAPI 会不会 async”，而是把 HTTP request lifetime 和 Agent job lifetime 又混回一起。正确边界是：API 接收命令、建立 Run、入队；Worker 独立 claim、执行、checkpoint、pause/resume。

1

先看最危险的“看起来很现代”写法

有 `async` 不代表架构就异步了。
❌ 长 Agent 绑在 HTTP request
@app.post("/research")
async def research(body):
    result = await agent.run(body)
    return result

客户端超时、反向代理超时、部署滚动重启，都和长任务绑死。

✅ HTTP 只建立 durable job
@app.post("/runs", status_code=201)
async def create_run(body):
    run = control.submit(...)
    return RunResponse.from_record(run)

真正执行发生在 Queue 后面的 Worker。

“能 await 20 分钟”不等于“应该 await 20 分钟”。Concurrency syntax 和 durable job architecture 是两层问题。

`async def` 里直接调用 blocking SDK，会真的卡 event loop

FastAPI 只会自动处理它自己调用的 path operation / dependency；你在 async 函数内部手动调用的普通函数，不会被“自动 threadpool 化”。
@app.get("/bad")
async def bad():
    # 普通同步函数，直接在 event loop 线程执行
    return blocking_sdk.fetch()

@app.get("/better")
async def better():
    return await anyio.to_thread.run_sync(
        blocking_sdk.fetch
    )
但 thread offload 只解决“别堵 event loop”。它不提供 checkpoint、retry ownership、跨进程恢复、worker lease 或 durable queue。
4

那直接把 endpoint 写成普通 `def` 呢？

FastAPI 会把同步 path operation 放进外部 threadpool，但这仍然只是请求执行模型。
写法FastAPI 怎么执行适合不代表
`async def` + awaitable I/Oevent loop 上 await短 I/O 请求后台任务系统
`def` endpointthreadpool同步阻塞 SDKdurable worker
`async def` + `to_thread`显式 thread offload少量同步阻塞调用无限并发
Queue → Worker独立 job lifecycle长 Agent / 可恢复任务只是“async 语法糖”
5

`BackgroundTasks` 什么时候好用，什么时候不够？

“response 返回后执行”与“durable background system”不是同义词。
适合

短小、同进程、失败后可以接受简单处理的收尾任务：通知、轻量日志、很小的文件处理。

不适合我们的主 Agent

几十分钟运行、需要多进程/多机 worker、checkpoint、retry、暂停审批、部署重启后继续。

一个判断题：如果 API 进程被滚动升级杀掉，你是否仍要求这项任务继续？如果答案是“必须”，就别只靠进程内 BackgroundTasks。
6

v5.3：Worker adapter 真正从 HTTP 边界外执行

POST 之后 Run 仍是 queued；Worker tick 才推进它。
HTTPPOST /runs → RunStore.create → Queue.enqueue → 201
Client已经拿到 run_id，可以断开连接
Workerqueue.pop → claim revision → execute Graph
RunStorequeued → running → completed / waiting_approval
async def run_one_worker_tick(bridge):
    job = bridge.control.queue.pop()
    if job is None:
        return

    outcome = await anyio.to_thread.run_sync(
        bridge.execute_job,
        job,
    )
    return outcome
这里 thread offload 发生在 Worker。即使底层 Graph adapter 暂时是同步接口，也不会把 FastAPI 用户请求拖住。
7

请求超时和 Job 失败必须是两种状态

否则你会把网络问题误判成 Agent 问题。
HTTP client timeout
≠
Run failed

POST 已成功提交并返回 201 后，客户端之后掉线并不会自动 cancel Run。反过来，Worker 失败也不意味着当初的 HTTP request 应该一直挂着等 retry。

8

并发限制应该放在哪些层？

“async 能并发”不代表任何资源都应该无限并发。
API连接/请求限流
Queue/Workerworker concurrency / lease
Provider/Toolrate limit / semaphore / budget

CPU、GPU、外部模型、数据库连接池都有自己的稀缺资源。不要用一个 `asyncio.gather()` 把所有限制抹掉。

故意失败：为什么“把 Worker 塞进 API BackgroundTasks”还是会后悔？

Deploy旧 API pod 收到 SIGTERM
Task进程内 background Agent 还在跑
Crash没有独立 lease / durable queue ownership
正确边界Run 已在 durable store，job 已在 broker，健康 Worker 可重新 claim/resume
