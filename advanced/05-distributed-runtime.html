一个 Worker 跑得稳，
不代表十个 Worker 不会互相踩死。

工程问题：Agent 任务可能跑几十分钟甚至几小时。Worker 会重启、网络会抖、Queue 会重复投递、旧进程会在 lease 过期后突然醒来。A5 把前面的 durable 概念真正拼成 at-least-once Queue + lease/heartbeat + fencing + checkpoint recovery + backpressure。

很多 Queue 都是 at-least-once delivery：消息可能重复出现。真正的 ownership 不能靠“我 pop 到了这条消息”，而要靠共享控制面里的 claim/lease。

Queue delivery 是建议你尝试工作；Lease 才是当前所有权。这两个概念混在一起，重复投递时就会出现两个 Worker 同时执行同一个 Agent。

为什么 heartbeat 还不够？Zombie Worker。

t=0    Worker A claim
       lease expires at t=30
       fence = 41

t=20   A 网络卡住 / GC pause / process freeze

t=31   watchdog: lease expired
       requeue

t=32   Worker B claim
       fence = 42

t=33   Worker A 突然恢复
       还以为自己是 owner

旧 Worker 不一定会主动收到“你已经失去所有权”。所以每次重要写入还要携带一个单调递增的 fencing token。共享下游看到 41 < 42，就拒绝旧 Worker。

5

重复投递：不要追求魔法 exactly-once

Queue delivers job #17
→ Worker A claim succeeds

Queue redelivers same logical attempt
→ Worker B receives duplicate
→ claim sees active lease / stale attempt
→ reject

Queue 可以重复；真正重要的是 重复 delivery 不产生第二个 owner。这比把所有希望压在 Queue 的“恰好一次”语义上稳得多。

End-to-end exactly-once 通常不是一个 Queue 配置能给你的。Run claim、checkpoint、external side effect、数据库 commit 都有各自失败窗口。

Backpressure：系统满了时，正确动作可能是“别收了”

Queue35 / 100
Tenant3 / 10
ACCEPT
没有 admission control 时，最容易出现的不是“任务都排着慢慢做”，而是 queue wait、内存、数据库连接、下游 rate limit 一起崩。入口应该能返回明确的 overload/retry signal。
8
Graceful drain：升级 Worker 不能直接 SIGKILL 一切
worker-a mode = DRAINING

已有 lease:
  heartbeat ✅
  checkpoint ✅
  finish ✅

新 delivery:
  claim ❌
这样 rolling deploy 时，Worker 先停止接新 Run，让当前工作结束或安全 checkpoint，再退出。如果超时还没结束，再由 lease expiry + recovery 接管。
