先别画技术栈，先写不可破坏的产品约束

Long-runningRun 最长数小时，HTTP request 不能拥有执行生命周期。
Multi-tenantRun / files / approvals / events / quotas 都必须 tenant scoped。
Untrusted world网页、RAG、文件、Tool output 都可能带 prompt injection。
Failure is normalWorker crash、重复投递、断网、外部 API ambiguity 都是正常路径。

“1000 用户”也不等于“1000 Worker”。用户并发、活跃 Run、排队 Run、Browser/Python 资源需求、LLM/provider rate limit 是不同的容量维度。

10
Final Interview Defense
一个 Worker crash 后，新 Worker 从 LangGraph checkpoint 成功恢复。是否就已经足够保证旧 Worker 不会破坏状态？
最终应该能 defend：① 为什么 API 不 inline 跑 Agent？② RunStore / Queue / checkpoint 为什么必须分开？③ duplicate delivery 如何不产生双 owner？④ zombie Worker 怎么挡？⑤ prompt injection 为什么是 authority 问题？⑥ MCP discovery 为什么不等于 permission？⑦ Python subprocess 为什么不是 sandbox？⑧ SSE 怎么恢复？⑨ 所有 span 200 为什么 quality 仍可能失败？⑩ ambiguous side effect 怎么处理？⑪ RunStore 挂了为什么要 fail safe？⑫ overload 为什么要拒绝新工作？⑬ graceful deploy 怎么做？⑭ 1000 users 怎么估 Worker/Browser/Python capacity？⑮ 为什么不要轻易说 exactly-once？
